# Spike #4/#5 · 取消响应与阻塞调用的打断代价

日期：2026-10-15
环境：arm64 macOS，libssh2 1.11.1（Homebrew，链接 OpenSSL 4.0.3）
服务器：`sftp-modern`（alpine 3.20 / OpenSSH 9.7），端口 2202
延迟注入：容器内 `tc qdisc add dev eth0 root netem delay 1000ms`（RTT ≈ 1 s，对齐方案 v2.3 的"跨国线路"口径）
负载：`/home/tester/spike/big.bin` 64 MB，chunk 256 KB，1 channel / 1 handle
测量：`Spike/Sources/SpikeRunner/CancelSpike.swift`，`spike cancel`

---

## 0. 结论先说

| # | 结论 | 影响 |
|---|---|---|
| 1 | **"取消响应多久"就是 poll 的超时切片，不是某个固定常量**：切片 50 / 200 / 1000 ms 实测 47.4 / 198.5 / 999.7 ms。 | v2.3 的出口标准"200 ms 内取消"不是算法属性，是**参数选择**。200 ms 切片实测 198.5 ms 属压线，工程上取 **50 ms** |
| 2 | **上一轮看到的"取消要 8 秒"和取消无关**。循环在 47 ms 内就退出了，8 s 全花在退出后的 libssh2 **体面关闭**（`close_handle` + `sftp_shutdown` + `disconnect`）上：1 s RTT 下 7.9 s ≈ 8 个往返；同一段代码零延迟只要 15–25 ms。 | 清理代价与 RTT 成正比，与取消时机无关。**取消路径上禁止调用体面关闭** |
| 3 | **改成"掐 socket"后取消总代价从 8.05 s 降到 0.20 s**：`shutdown(fd, SHUT_RDWR)` + `session_free` + `close` 实测 0.0–0.4 ms，之后无挂起、无崩溃、服务端正常回收。 | 定案：取消 = 置标志 → 等循环退出（≤60 ms）→ 直接 abort 该连接 |
| 4 | **建阶段（`sftp_init` / `open`，仍是阻塞调用）里的取消完全无效**：置标志后要等 3.5 s 才回到循环顶部，且这段延迟与 poll 切片无关（50/200/1000 三轮都是 3529–3549 ms）。 | 慢速线路上"连接中 / 打开中"的取消点不动。**M0b 必须把建阶段也纳入同一个非阻塞循环**，否则只有传输中可取消 |
| 5 | **唯一能立刻打断阻塞 libssh2 调用的手段是 `shutdown(socket)`**：调用本身 0.09–2.3 ms，被卡住的调用 2.5–3.0 ms 内返回错误（`-36 Broken pipe or socket`，或 `sftp_init: Unable to startup channel`），随后 `disconnect` / `session_free` 各 ≤0.5 ms。 | 可作兜底：标志置了但循环迟迟不退出时直接掐。代价是**这条会话作废，不能归还连接池** |
| 6 | **libssh2 在 `set_blocking(0)` 之后自己把 socket 设成非阻塞**：预先置 `O_NONBLOCK` 与不预置的实测完全一致（197.4 vs 198.5 ms，`read调用=0 EAGAIN=1 poll=1 超时=1` 逐字段相同）。 | Core 不需要管理 socket 标志位，也不会因为"忘了设非阻塞"而假死 |

## 1. #4 取消响应 = poll 切片（RTT 1 s，parked 模式）

`parked` 模式等建阶段（`sftp_init` + `open`，阻塞）跑完、确认循环已停在 poll 边界后才置取消标志。
建阶段耗时稳定 5.03–5.09 s ≈ 5 个 RTT，正好复现 §M0a-02 结论 5 里"每次传输新建约 5 个往返"。

| poll 切片 | 取消→循环退出 | 循环退出→线程返回（体面关闭） | 拆连接 | 计数 |
|---|---|---|---|---|
| 50 ms | **47.4 ms** | 9045.0 ms | 1.4 ms | `read=0 EAGAIN=1 poll=1 超时=1` |
| 200 ms | **198.5 ms** | 7876.1 ms | 2.2 ms | 同上 |
| 1000 ms | **999.7 ms** | 7060.5 ms | 0.1 ms | 同上 |
| 200 ms + 预置非阻塞 socket | 197.4 ms | 7867.0 ms | 0.1 ms | 同上（对照组，见结论 6） |

`read调用=0 / 已传 0 B / poll=1 超时=1`：取消发生在**第一次 poll 超时**上，一个字节都还没读回来。
所以 8~9 s 不可能是"读完在途数据"的成本——它纯粹是关闭动作的往返。

## 2. 取消收尾：体面关闭 vs 掐 socket（RTT 1 s，切片 200 ms）

| 取消点 | 收尾方式 | 取消→循环退出 | 清理（handle/channel） | 拆连接 | 合计 |
|---|---|---|---|---|---|
| poll 边界 | 体面关闭 | 197.3 ms | **7855.5 ms** | 0.7 ms | 8.05 s |
| poll 边界 | 掐 socket | 196.2 ms | **0.1 ms** | 0.2 ms | **0.20 s** |
| 建阶段 | 体面关闭 | 3549.2 ms | 2028.1 ms | 0.7 ms | 5.58 s |
| 建阶段 | 掐 socket | 3527.1 ms | **0.0 ms** | 0.4 ms | 3.53 s |

体面关闭那 7.9 s 的来源：`runMultiplexed` 退出前会 `set_blocking(1)` 再逐个 `close_handle` / `sftp_shutdown`，
每个都要一个完整 RTT；1 s 延迟下 8 次往返就是 8 秒。零延迟对照实验里同一段只需 15–25 ms（见 §5）。

**建阶段那一行两组都是 3.5 s**：掐 socket 也救不了，因为标志根本传不进正在阻塞的 `sftp_init`。
这是结论 4，也是 §6 里给 M0b 的第二条硬约束。

## 3. #5 阻塞调用被打断（RTT 1 s）

阻塞模式下 `readRangeBlocking`（8 MB，256 KB chunk）跑在线程里，主线程 1.5 s 后调 `shutdown(fd, SHUT_RDWR)`：

| 指标 | 注入 1 s 延迟 | 零延迟 |
|---|---|---|
| `shutdown()` 调用本身 | 0.090 / 0.113 / 2.279 ms | 0.016 ms（rc=0） |
| 被打断 → 阻塞调用返回 | 2.5–3.0 ms | 0.3 ms |
| 返回的错误 | `sftp_init: Unable to startup channel` | `-36 Broken pipe or socket` |
| 之后 `disconnect` / `session_free` | 0.0–0.5 / 0.0–0.2 ms | 0.1 / 0.1 ms |

即打断本身极便宜，且打断后 session 可以安全释放（不挂、不崩）。
注意错误文案随"卡在哪个调用"而变，Core 不能靠字符串判断，要按 `libssh2_session_get_blocking` 前的 errno/返回码分类；
被打断的会话一律标为"作废"，不回收进池。

## 4. 为什么"200 ms 内取消"这条出口标准需要重新表述

原口径把取消当成一个算法属性。实测说明它是三段之和：

```
用户点取消 → [≤ poll 切片] → 循环退出 → [清理，可选] → 连接不可用
                可控（50 ms）              体面关闭 = N×RTT，必须省掉
```

- 判定"取消是否达标"只看第一段，必须显式写成 **poll 切片 ≤ 50 ms**。
- 若 UI 要等到"连接彻底释放"才算取消完成，则 1 s RTT 下 7.9 s 的清理会被算进取消延迟——这正是本轮开始前观察到的假象。

## 5. 零延迟对照（netem 已移除）

| 场景 | 取消→循环退出 | 清理 | 拆连接 | 备注 |
|---|---|---|---|---|
| parked，切片 200 ms | 0.1 ms | 24.8 ms | 0.0 ms | 取消点落在 `循环顶部`，已传 90 KB，`poll=6 超时=0`（本地响应快于切片，poll 不超时） |
| setup，稳定 0.05 s | 0.6 ms | 15.8 ms | 0.1 ms | 同上，本地建阶段只 8 ms，取消落在循环顶部 |

本地零延迟下"取消→用户可见停止"是亚毫秒级；上面所有秒级数字都来自 RTT，不是 CPU 或 libssh2 内部开销。
（对照 M0a-02 的提醒：本机 loopback 走 Docker 用户态转发，吞吐有 ~130 MB/s 上限；延迟数字仍是真的，因为 netem 打在容器网卡上。）

## 6. 落到 ADR-0001 / M0b 的设计约束

1. **poll 切片 50 ms**，取消标志在"循环顶部"和"poll 超时"两处检查（已实现，直接进 Core）。
2. **取消路径不调用体面关闭**：循环退出后立刻 `shutdown(fd, SHUT_RDWR)` → `session_free` → `close`；`close_handle` / `sftp_shutdown` / `disconnect` 只用于**正常完成**的会话回收。
3. **会话池要区分两种状态**：`可复用`（正常结束）与 `已 abort`（作废，直接丢弃）。abort 过的 session 不能归还。
4. **建阶段（握手、认证、`sftp_init`、`open`）必须同样非阻塞 + poll + 取消检查**，否则"连接中/打开中"不可取消；这条决定 M0b 的 Session 抽象不能只包一个"传输循环"，要包整个调用状态机。
5. **`shutdown()` 是兜底而非主路径**：它能把阻塞调用 3 ms 内打断，但会话作废；只在"置标志后超过阈值仍未退出"（例如建阶段）时使用。
6. socket 非阻塞由 libssh2 自己维护，Core 不必设 `O_NONBLOCK`。

## 7. 复现

```bash
# 注入 1 s 延迟（容器已有 NET_ADMIN 权限）
docker exec ferry-sftp-modern-1 tc qdisc add dev eth0 root netem delay 1000ms

cd Spike && swift build
# 切片扫描 / 体面关闭 vs 掐 socket / 建阶段 vs poll 边界
SPIKE_POLL_TIMEOUTS=50,200,1000 SPIKE_CANCEL_MODES=parked,setup .build/debug/SpikeRunner cancel
SPIKE_CANCEL_ABORT=1 SPIKE_POLL_TIMEOUTS=200 SPIKE_CANCEL_MODES=parked,setup .build/debug/SpikeRunner cancel
# 非阻塞 socket 对照组
SPIKE_NONBLOCK_SOCKET=1 SPIKE_CANCEL_ABORT=1 SPIKE_POLL_TIMEOUTS=200 .build/debug/SpikeRunner cancel

# 撤掉延迟（务必，否则后续吞吐实验全被污染）
docker exec ferry-sftp-modern-1 tc qdisc del dev eth0 root
```
