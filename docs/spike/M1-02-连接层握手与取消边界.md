# M1-02：M1'-2 连接层 —— 握手、算法协商、主机密钥判定与取消边界

对应任务 #18。出口标准：Core 里定连接契约，Backends/SFTP 用 libssh2 实现握手与 session 建立，覆盖算法协商、hostkey 回调、超时，以及 ADR-0001 的取消边界（一个取消边界独占一条 session、poll 切片 ≤50 ms、禁止体面关闭）。产物链的是 M0b-03 的静态 xcframework。

## 0. 结论

1. **五台全部握手成功**，用的是要发布的那条代码路径（`SFTPBackend` + `SFTPConnection`），不是 spike 里的临时壳。全部协商参数逐个记在 §3。
2. **libssh2 的默认算法集本身就允许弱算法**：不带任何策略时，2204 直接谈成 `diffie-hellman-group14-sha1` + `ssh-rsa` + `aes256-cbc` + `hmac-sha1`——S6 列的四类弱算法（DH-SHA1、ssh-rsa、CBC、hmac-sha1）**一次全中**。所以"允许弱算法"这个开关不可能交给 libssh2 的默认值，必须由 Ferry 自己带一份白名单。这是本轮对基线影响最大的一条。
3. **libssh2 没有主机密钥回调**。密钥只能在 `libssh2_session_handshake()` 返回之后用 `libssh2_session_hostkey()` 取，所以 N3 定的 TOFU 判定只能落在"KEX 之后、认证之前"。实现照此摆放，并且真的在返回前拒绝：信任判定抛错 ⇒ 握手抛 `.hostKeyMismatch`、session 转 `aborted`、一个凭据字节都不发。
4. **`libssh2_session_method_pref` 静默剔除它不认识的算法名**。只有整串被剔空才返回 `-33`。"策略里写了个没编进来的算法"不报错，只是那条偏好消失 ⇒ 加了事后校验：实际协商值必须落在策略集合内，否则判协议违规（§6.2）。
5. **取消按时**：黑洞监听（服务器 accept 之后一个字节都不发）下，置标志 → `handshake()` 抛出实测 3 / 37 / 48 ms，全部 ≤ 一个 50 ms 切片加调度；同一案例里 poll 睡满 7 个超时片，7×50 ms ≈ 在飞 358 ms，说明等待确实是被切片切开的，不是睡死。
6. **超时是自家机器管的**：`handshakeTimeout=300 ms` → 301 ms 抛 `.network(.timeout)`，与内核或 `libssh2_session_set_timeout` 都无关。
7. **D7 可证伪**：每条连接绑一条自建串行执行器，握手的每一步记录线程号，实测 `executorThreads.count == 1`（五台与黑洞两种路径都是）。
8. 测试分两组：回环组 7 条任何时候可跑，真机组 5 条用 `FERRY_LIVE_SERVERS=1` 打开；两组全绿（回环组默认跑 12 条中 7 跑 5 禁）。

## 1. 契约形状（Core 侧新建）

`Packages/Core/Sources/FerryCore/Connection/`：

| 类型 | 职责 |
|---|---|
| `Endpoint` | host / port / username，**不含凭据**，可以进日志与存储 |
| `AuthenticationMethod` | `password` / `privateKey` / `sshAgent` / `keyboardInteractive`；`CustomStringConvertible` 一律脱敏，`dump()` 不过滤（类型上写明了） |
| `ConnectionPolicy` | connect / handshake 两个预算 + `AlgorithmPreferences` |
| `AlgorithmPreferences` | kex / hostKey / encryption / mac 四个维度的名字数组；`libraryDefault` = 什么都不设 |
| `CancellationFlag` | 一次性、原子、记录首次置位时刻；`OSAllocatedUnfairLock` 托底 |
| `HostKey` + `HostKeyTrust` | 线路取到的密钥 blob、`SHA256:` 指纹，以及信任判定的接缝 |
| `NegotiatedSession` | banner + 主机密钥 + 六个维度的**实际协商值** |
| `RemoteConnection`（`protocol : Actor`） | `handshake()` / `nonisolated cancel()` / `phase` / `close()` |
| `RemoteBackend` | `declaredCapabilities` + `makeConnection(_:)` |

与 v2.3 的三处有意偏差（同格式记进 `docs/ADR-0000` §10）：

- v2.3 §101 的 `RemoteFileSystemFactory` 改名 `RemoteBackend`：M1' 之后 FTP 后端要做同一件事，工厂的名字太窄。
- 契约里**不含** `fileSystem` 与 `negotiatedCapabilities`，推到 #21。先要求这两个成员只能交出一个抛"未实现"的壳，而抛错的方法在类型上看不出来没实现，比缺成员更坏。
- `RemoteConnection` 直接做成 `Actor`，取消走 `nonisolated func cancel()`。ADR-0001 D3 要求取消从 UI 线程即刻生效，`actor` 隔离下唯一不排队的方法就是 `nonisolated`；这与 D7"全部 C 调用困在一条执行器上"是同一套机制的两面。

## 2. 实现摆放

`Packages/Backends/Sources/FerryBackendsSFTP/`：`SessionExecutor`（串行执行器 + 当前线程号）、`TCPStream`（非阻塞 connect + 切片 poll）、`SessionLoop`（EAGAIN→`block_directions`→poll 切片的状态机）、`SFTPConnection`（actor，绑执行器）、`SFTPBackend`。

一次 `handshake()` 的顺序：非阻塞 TCP connect → `libssh2_session_init_ex` → `set_blocking(0)` → `set_timeout` → 算法偏好 → `drive { libssh2_session_handshake }` → banner 校验 → 取主机密钥 → 取六维协商值 → 策略反查 → `HostKeyTrust.evaluate`。任何一步失败 ⇒ `shutdown(fd, SHUT_RDWR)` → `session_free` → `close(fd)`，phase 转 `aborted`（D4、D6）。

三个决定值得记：

- **非阻塞在 handshake 之前设**（D5"建阶段也走同一台机器"），所以 banner 等待、KEX 全过程都在我们的 poll 切片里，取消与超时才有统一的落点。
- `TCPStream` 的 connect 切片与 `SessionLoop` 的等待切片共用一个常量 `pollSliceMs = 50`，共用一只 `LoopStats`。计数做成引用类型是有意的：握手的每一段写同一只盒子，抛错退出时计数已经在 actor 状态里——"局部 struct 再拷回来"会在最需要数据的取消/超时路径上恰好丢掉（本轮真踩过，改前黑洞实验里 `poll=0`）。
- **认证一个字节的代码都没有**接进握手。信任判定被挪到返回之前这件事，靠实现里根本没有 auth 调用来保证，不是靠约定。

|---|---|---|---|---|---|
| 2201 | `diffie-hellman-group-exchange-sha256` | `ssh-rsa` | `aes128-ctr` | `hmac-sha1` | 主机密钥换成 4096 位 RSA（blob 535 B） |
| 2202 | `diffie-hellman-group-exchange-sha256` | `ssh-ed25519` | `aes128-ctr` | `hmac-sha1` | 同一台服务器，客户端偏好一换结果全换 |

### 3.3 只留现代算法（客户端拒绝弱算法）

| 端口 | 结果 |
|---|---|
| 2201 | 成：`curve25519-sha256` + `ssh-ed25519` + `chacha20-poly1305` + `hmac-sha2-512-etm@openssh.com` |
| 2202 | 成：同上 |
| 2203 | **败**，7–12 ms，`LIBSSH2_ERROR_KEX_FAILURE(-5)` |
| 2204 | **败**，7–16 ms，`-5` |
| 2205 | 成：`curve25519-sha256@libssh.org` + `ssh-ed25519` + `chacha20-poly1305` + `hmac-sha2-512-etm@openssh.com` |

两个要点：**老服务器不等于必须弱算法**——真老发行版 2205（6.7p1 / OpenSSL 1.0.1t）能谈一套全现代的；以及"关掉弱算法"在 libssh2 这条路上表现为 KEX 直接失败，而不是"降级成功"，所以 #24 的失败样本要按 `-5` 认，不能按"协商出的值"认。

### 3.4 指纹格式与 OpenSSH 对齐

`HostKey.fingerprintSHA256` = `SHA256:` + 对线路 blob 做 SHA-256 后的**去填充** base64。逐台与 `ssh-keygen -lf` 比对：

- 2201（ed25519、4096 位 RSA）、2202（ed25519、ecdsa、3072 位 RSA）、2205（RSA 2048、ecdsa）：`ssh-keyscan` 取密钥 → `ssh-keygen -lf` 打指纹，与我们算的逐字符相同。
- 2203/2204 **`ssh-keyscan` 在 Mac 上拿不到密钥**（本机 OpenSSH 10.3 不接受它们唯一那条 DH-SHA1 KEX，扫描阶段就失败），改为在容器内对 `/etc/ssh/ssh_host_rsa_key.pub` 跑 `ssh-keygen -lf`：`89DaPf04…`、`QQs8YZIq…` 与线路值一致。
- 附带结论：以后要在仿真环境里"用 OpenSSH 客户端交叉验证老服务器"，2203/2204 必须从容器内或使用放开老算法的客户端配置，本机 `ssh` 会静默拿不到 key。

单测里另有两个固定向量（ed25519 / RSA blob → 指纹），与 `ssh-keygen` 输出一致，跑在 `Packages/Core/Tests/CoreTests/ConnectionTests.swift`。

## 4. 取消与超时实测

量法：回环上真服务器几十毫秒就握完手，切片测不出来。所以本地起一个**只 accept、一个字节都不回、也故意不关**的监听 socket（`StallListener`），复现"服务器连 banner 都不发"。这是 M0a-03 用 `tc netem` 拉 1 s 延迟的轻量替代，不需要 root，也不需要动容器。

| 场景 | 观测 |
|---|---|
| 在飞 300 ms 后 `cancel()` | 置标志 → `handshake()` 抛 `CancellationError`：**3 / 37 / 48 ms**（三次） |
| 同一次的计数 | `EAGAIN=7`、`poll=8`、`超时片=7`、线程=1；7×50 ms ≈ 在飞 358 ms |
| 取消后调 `close()` | **0 ms**，phase 仍 `aborted`（不补体面关闭；M0a-03 实测那条路 8.05 s） |
| `handshakeTimeout=300 ms`，不取消 | **301 ms** 抛 `.network(.timeout)`，phase `aborted` |
| 端口拒连 | 立刻抛 `.network(.connectionRefused)`，phase `aborted` |

`cancel()` 是 `nonisolated`，从测试所在线程直接置位而不经 actor 队列——这是 D3 能守住的原因：如果置位也要排队，而 session 线程正睡在一个 50 ms 切片里，取消延迟就会变成"排队 + 切片"。

## 5. 线程与 session 归属（D2 / D7）

`SFTPConnection` 是 actor，`unownedExecutor` 指向自己那条 `DispatchQueue(label: "local.ferry.sftp.session")`；`SessionExecutor.enqueue` 用 `UnownedJob.runSynchronously(on:)` 把任务钉在该队列上。每次跨 libssh2 调用的边界都 `visitedThreads.insert(currentThreadID())`，实测：

- 五台真机：`executorThreads.count == 1`
- 黑洞路径（含被取消的那条）：`executorThreads.count == 1`

fd 与 `LIBSSH2_SESSION *` 因此都是 actor 隔离状态，实现里没有一把自加的锁。一条连接 = 一条 session = 一个取消标志 = 一条执行器，正是 D2 的形状；`handshake()` 的 `phase` 门（`.idle` 才走、`.ready` 返回缓存、`.connecting` 报协议违规、`.aborted/.closed` 报 `connectionLost`）保证同一取消边界不会被两条流水线共用。

## 6. 两个 libssh2 的坑

### 6.1 没有主机密钥回调

头文件里与主机密钥相关的取用只有 `libssh2_session_hostkey(session, &lenp, &type)`，且必须握手返回之后调；`libssh2_session_knownhost_*` 一族是"拿我们自己存的 known_hosts 去比"，不是回调。于是：

- 信任判定的位置被 libssh2 定死了：**KEX 之后、认证之前**。这就是"hostkey 回调"在本项目里的实际形状——Core 侧的 `HostKeyTrust` 接缝，由后端在返回 `NegotiatedSession` 之前 await。
- 代价是可接受的：KEX 已经做完，中间人此时已能观察到流量，但凭据还没发出。#19 的 `HostKeyStore` 只需挂在这个接缝上。
- `libssh2_session_hostkey` 返回的 `type` 对证书/未知类型可能是 `LIBSSH2_HOSTKEY_TYPE_UNKNOWN`，所以实现**没有**按 type 硬失败（早前一版写了硬失败，会把 `ssh-ed25519-cert@openssh.com` 之类直接打死），而是把 `type=`/`len=` 塞进"取不到主机密钥"的诊断信息里。算法名一律用协商到的 `LIBSSH2_METHOD_HOSTKEY` 字符串。

### 6.2 `method_pref` 静默剔除未知算法名

`ThirdParty/build/src/libssh2/src/kex.c:4214` 起的循环按逗号切串，认不出的名字直接从新串里抹掉；只有抹到空串才返回 `-33 METHOD_NOT_SUPPORTED`。KEX 维度还有一层：libssh2 会在我们给的串前面拼上 `ext-info-c,kex-strict-c-v00@openssh.com`，所以**kex 的偏好串永远不会空**，写一堆不存在的 kex 名只会得到"广告列表里没有真算法 ⇒ 服务器拒绝 ⇒ `-5 KEX_FAILURE`"。实测两格（打到 2202）：

| 传入 | libssh2 行为 | 我们看到的错误 |
|---|---|---|
| `keyExchange: ["ferry-bogus-kex@example.com"]` | 静默剔空真实部分，只剩 ext-info 标记 | 30 ms 后 `-5` |
| `mac: ["ferry-bogus-mac@example.com"]` | 整个串被剔空 | 立刻 `-33` |

于是加了事后反查：`verifyNegotiatedWithinPolicy(实际协商值, 策略)`，六个维度任一越界就抛 `.protocolViolation`，session 一样硬拆。理由写进代码注释——策略被放宽一定会在这里露出来，而策略被"抹掉一条"不会。这条守卫在真机上凑不出触发样本（libssh2 不会主动谈策略外的算法），所以做成自由函数由单测直接构造。

顺带一条诊断事实：`-5`（对面不接受）与 `-33`（我们这侧不支持）经 `ErrorTaxonomy` 都是 `protocolViolation`，`diagnosticCode` 分不开，只能靠 detail 里的 `rc=`。#24 出矩阵时失败列要按 **raw rc** 分，别按诊断 token 分。
