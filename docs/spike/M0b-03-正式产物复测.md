# M0b-03 · 正式产物复测（钉版 xcframework + 10 条 CVE 补丁）

日期：2026-10-15
被测产物：`ThirdParty/build-xcframework.sh` 生成的 `Packages/Backends/Vendor/FerrySSH.xcframework`
（OpenSSL 3.5.9 + libssh2 1.11.1 + 本地补丁系列，静态，arm64/x86_64 fat）
复测范围：ADR-0001 §6 的"M0b 出口必测清单"5 条，一条不落
对照基线：M0a-02 / M0a-03 / M0a-04 / M0a-05 / M0b-01（当时全部跑在 Homebrew libssh2 上）

为什么要重跑：M0a 的所有事实都来自 Homebrew bottle，那份 libssh2 链的是 **OpenSSL 4.0.3**，
而交付产物用的是我们自己编的 OpenSSL 3.5.9 + 钉死 commit 的 libssh2。crypto 后端换了，
吞吐、私钥解析、阻塞调用被打断的绝对值都可能变；协议层结论理论上不变，但要实测才算数。

## 0. 结论先说

| # | 结论 | 影响 |
|---|---|---|
| 1 | **产物可被 SwiftPM 链接，链的是静态库不是 dylib**。`Packages/Backends` 的 3 个链接测试通过；`otool -L SpikeRunner` 里没有任何 ssh2/ssl/crypto 动态库引用，`nm -arch arm64` 数到 `_libssh2_*` 共 293 个符号、其中 122 个已定义（T/t）、**undefined 为 0**，另有 1000 个已定义的 OpenSSL 符号。`libssh2_crypto_engine()` 返回 **openssl**，确认用的是我们编的那份 OpenSSL 3，不是 Homebrew 的 4。 | #14 出口达标：`Vendor/FerrySSH.xcframework` 可以直接进 Backends，不需要再留 `.systemLibrary` 的临时壳 |

### 产物哈希不可复现（实测）

| 操作 | 结果 |
|---|---|
| 全量构建跑 3 次（源码、补丁、编译参数完全相同） | `8634f86e…` / `3a0cdeca…` / `c9b71d20…`，三个不同 |
| 手工 `libtool -static` 同一秒内连跑两次 | 相同（`3c7a119e…`） |
| 手工 `libtool -static` 隔 3 秒再跑两次 | `286b8644…` / `5c5e6fc1…`，不同 |

原因是 `libtool -static` 给归档成员写入**当下时间戳**。所以：
- 别把"重建一遍比 sha256"当验收手段，必然失败；
- 要复现内容一致，钉的是上面那三行源码指纹；
- 产物哈希仍然有用，它是"本次构建的身份证号"，用来把客户机上的二进制和某份构建日志对上。

顺带核实：xcframework 里的切片和 `merged/FerrySSH.a` 字节相同（`xcodebuild -create-xcframework` 不改写归档），
所以 provenance 里那个哈希确实描述的是最终交付的那份字节。

## 2. 差点记错一轮数据：产物换了，二进制没换

第一轮"补丁版复测"我是这么跑的：`swift build --build-path .build/out`，再执行
`.build/out/Products/Debug/SpikeRunner`。看着没问题——构建报了 `Build complete!`，`lipo` 也确认 arm64。

但它跑的是**上一轮未打补丁**的产物。`.build/out` 里已经有一个 `buildPath` 配置，
`--build-path .build/out` 叠上去变成 `.build/out/out/Products/Debug/`，新的二进制落在那里，
我执行的是 `.build/out/Products/Debug/` 下 15:30 那个旧文件。时间戳看不出问题——构建命中缓存时本来就不重写文件。

发现方式不是看时间，是看内容。CVE 补丁引入了只有打完补丁才存在的字符串字面量：

| 标记 | 出处 | vendor 归档 | 旧二进制 | 新二进制 |
|---|---|---|---|---|
| `ListFetch data too short` | 0005 | 有 | **无** | 有 |
| `username_len out of bounds` | 0001 | 有 | **无** | 有 |
| `Too many publickey attributes` | 0009 | 有 | — | 有 |

旧二进制两个标记都是 0 次——它链的是未打补丁的 libssh2。据此把整轮数据作废重跑，
并把判据固化成 `Spike/Scripts/verify-linkage.sh`（跑之前比内容，不比时间；vendor 有而二进制没有就退出 1）。

**代价**：这期间得出的两个结论都是错的，而且错得很像发现——
(a) "补丁把取消响应从 0.0 ms 变成 1.9 ms"；(b) "`symlink_ex` 在自编产物上返回码变正常了，M0a 的结论翻转"。
(b) 恰好是因为那轮用的是未打补丁产物，而真正的补丁版又回到了 `-31`。
教训写进 §0 结论 6：**凡是"换了产物"的复测，先证明二进制里装了新产物，再谈数据。**

## 3. spike #7 · API 存在性（`Spike/Scripts/api-probe.sh`）

探针改写过：以前是给每个符号真链一个 dylib，现在产物是静态归档，链接期探针不成立。
改成两段——`clang -fsyntax-only` 查**声明**（头文件里有没有），`nm --extern-only` 查**定义**（归档里有没有）。

```
汇总：声明 23/25，定义 23/25
两头都没有：libssh2_session_set_abort_fn、libssh2_transport_set_sendsize
```

与 M0a-05 在 Homebrew 上的结果**逐个符号一致**。补丁只动 `src/*.c`，10 个补丁的 diff 里没有 `include/`，
所以 API 面不变是预期的，实测也确认了。

真正的"链得上"证明不是这个脚本，是 Spike 自己：`Spike/Package.swift` 已删掉
`.systemLibrary` + `unsafeFlags(["-L/opt/homebrew/lib"])` + `linkedLibrary("ssh2")`，
改成依赖 `Packages/Backends` 的 `FerrySSHShim`。它能 build 出可执行文件并跑通 §4–§7，就是链接成立的证据。

## 4. spike #4/#5 · 取消三段计时与打断代价（netem 1 s）

环境同 M0a-03：容器出口 `tc qdisc add dev eth0 root netem delay 1000ms`，64 MB 文件，1 channel。
下表每个数字都在**打完 10 条补丁的产物**上重测，右边是 M0a-03 的 Homebrew 值。

| 测量项 | 正式产物 | M0a-03（Homebrew） | 判定 |
|---|---|---|---|
| 取消→循环退出，切片 50 ms | **40.1 ms** | 47.4 ms | 复现：取消响应就是切片 |
| 取消→循环退出，切片 200 ms | **198.4 ms** | 198.5 ms | 复现 |
| 取消→循环退出，切片 1000 ms | **999.1 ms** | 999.7 ms | 复现 |
| 体面关闭耗时（循环退出后） | **7047–8158 ms** | 7876–9045 ms | 复现：秒级，与 RTT 成正比 |
| 掐 socket 收尾（清理 + 拆连接） | **0.2 + 0.1 ms** | 0.0–0.4 ms | 复现：8 s → 亚毫秒 |
| 建阶段取消延迟（切片 50/200/1000） | **3535.8 / 3534.2 / 3553.4 ms** | 3529–3549 ms | 复现：与切片无关，建阶段不可取消 |
| `shutdown()` 本身 | **0.069 ms** | 0.09–2.3 ms | 复现 |
| 被打断的阻塞调用返回 | **27.5 ms** | 2.5–3.0 ms | 复现：仍是"几十毫秒"级，不是 3.5 s |
| 3 条空闲 channel 连带 | **打断前 3 个，打断后 0 个**，探测 0.9 ms | 3 → 0，0.1–0.6 ms | 复现：损失是全量的 |
| 预置 `O_NONBLOCK` 对照组 | 199.9 ms（不预置 199.5 ms，计数字段相同） | 197.4 vs 198.5 ms | 复现：Core 不用管 socket 标志位 |

建阶段耗时 5023–5147 ms ≈ 5 个 RTT，和 M0a-02 的"每次传输新建约 5 次往返"对上。

> 注：M0a-03 的"取消→循环退出 0.0 ms"那组是**零延迟**对照，不能和本表比。
> 零延迟下本轮（同一个 10 补丁二进制）实测 0.0–1.7 ms，量级一致。

结论：ADR-0001 §7 的 7 条设计约束（切片 50 ms、取消路径不走体面关闭、abort 过的 session 不归还池、
建阶段必须纳入同一个非阻塞循环、`shutdown` 只作兜底、Core 不管非阻塞标志、一个取消边界 = 一条 session）
**全部在交付产物上成立，ADR 不改**。

## 5. spike #2/#3 · 吞吐、CPU 与请求重叠（netem 15 ms）

负载 64 MB / 256 KB 请求，各 3 轮取中位数。

| 方案 | 并发 | MB/s | 每核 MB/s | M0a-02 的 MB/s | 判定 |
|---|---|---|---|---|---|
| 单Session单Channel | 1 | 36.8 | 230.4 | 32.5 / 192.6 | 复现 |
| A 多Session池 | 2 | 59.2 | 226.2 | 48.1 / 192.4 | 复现 |
| B 单Session多Channel | 2 | 35.3 | 235.9 | 35.2 / 199.4 | 复现 |
| A 多Session池 | 4 | 55.2 | 230.8 | 68.2 / 200.5 | 复现（本轮偏低，见下） |
| B 单Session多Channel | 4 | 57.2 | 261.3 | 36.3 / 193.6 | 本轮偏高：M0a-02 同档波动就有 35–52，本轮 51–57 |
| A 多Session池 | 8 | **68.5** | 219.0 | 89.0 / 212.2 | 复现"只有多连接才涨" |
| B 单Session多Channel | 8 | 40.1 | 241.6 | 39.5 / 198.5 | 复现"B 换不来吞吐" |
| C' 同Channel串行（对照） | 2 / 4 / 8 | 37.9 / 28.1 / 26.6 | 216.1 / 201.9 / 187.5 | 30.4 / 36.9 / 32.0 | 复现：同一 channel 上把并发摊平只会更慢，不涨 |

- **方案 C（同 channel 请求流水线）仍然不可实现**：2/4/8 三路全失败，
  `code=-31 sftp_status=0 sftp_read() internal error`，与 M0a-02 结论 1 逐字一致。
- **A 与 B 的高低只在 2 档和 8 档是干净的**（59.2 vs 35.3、68.5 vs 40.1）。4 档本轮 55.2 vs 57.2
  打平，而 M0a-02 是 68.2 vs 36.3——B 这一轮冲到了它自己在 M0a 的波动上沿（本轮 51–57，M0a 记 35–52）。
  这不足以说"B 反超"，但足够说明**单档 MB/s 有 ±40% 抖动，M0b 不用绝对吞吐值定池大小**。
- **每核吞吐 187–261 MB/s**，M0a 是 190–240 MB/s。换 crypto 后端（OpenSSL 4 → 3.5.9）
  让绝对值有 ±10% 量级的移动，但"**CPU 成本与方案无关**"这条不变——
  选 A 还是 B 仍然不能用"省 CPU"论证。
- 单请求最大返回 262144 B（libssh2 内部 32 KB 分包 + read-ahead），结论 6 复现。
- 小请求（8 × 1 KB）：阻塞串行 23.92 ms/请求、非阻塞单 channel 22.42 ms/请求，
  M0a 是 23.5 ms/请求 ⇒ 结论 5"每次传输新建连接很贵"复现。
  多 channel 更贵：8 channel 要 103.41 ms/请求。

绝对 MB/s 依旧不能外推到真实 WAN（Docker 用户态端口转发 + 容器内单向 netem），
和 M0a-02 的免责一致。本轮只用于确认三条**排序性**结论没变：
多连接（A）是唯一能把吞吐推上去的手段、单连接多 channel（B）推不上去、
同 channel 请求流水线（C）在 libssh2 上做不到；CPU 成本与方案无关。

## 6. spike #8 · 私钥格式与认证

`libssh2_crypto_engine() = openssl`（自编 OpenSSL 3.5.9）。全部 13 个用例，
与 M0a-05 的判定完全一致：

耗时列是**空载机器上把 `spike keys` 连跑两遍**得到的，给的是每个用例两遍的最小–最大值
（判据先过 `verify-linkage.sh`，确认二进制链的是当前 10 补丁归档）。
bcrypt 解锁是纯 CPU 活，机器上一有并发构建就整体抬高——全套 spike 那遍（与其他任务抢 CPU）
给出 519–826 ms，不是后端的回归，所以这里只用空载样本。

| 用例 | rc | 耗时ms（空载两遍） | M0a-05（Homebrew） |
|---|---|---|---|
| ed25519 openssh 格式 + bcrypt 口令（frommemory / fromfile） | 0 / 0 | 457.2 / 453.3，445.6–581.4 | 450–500 ms |
| ed25519 openssh 格式无口令 | 0 / 0 | 16.8–18.9 | 26–32 ms |
| rsa3072 openssh + bcrypt | 0 / 0 | 441.8–525.6 | 同量级 |
| ecdsa256 openssh + bcrypt | 0 / 0 | 435.5–722.5 | 同量级 |
| rsa2048 老式 PEM + 口令 | 0 / 0 | 17.1–20.1 | 23 ms |
| ed25519 口令错误（frommemory） | **−16** | 247.5–356.7 | −16 |
| ed25519 口令错误（fromfile） | **−16** | 218.3–235.1 | −16 |
| 私钥文件不存在 | −16 | 0.0 | −16 |

- **`frommemory` 可用**，Keychain 取出的字节可直接喂进去，不需要写 Swift 预解析器（v2.3 的判定条件在正式产物上满足）。
- **bcrypt 解锁仍比明文贵 20 倍以上**（436–581 ms vs 16.8–20.1 ms）⇒ 认证后必须复用 session。
- 换后端没有改变错误文案：**同一个"口令错"，`frommemory` 报 `Unsupported private key file format`，
  `fromfile` 报 `Wrong passphrase or invalid/unrecognized private key file format`**。
  ErrorTaxonomy 里"口令错"和"格式不支持"不能只靠 `libssh2_session_last_error` 的字符串区分，
  这条与 M0a-05 一致，仍然有效。
- `libssh2_agent_init(NULL)` 段错误的老约束不变；传 session 后 `agent_connect` rc=0、
  `agent_list_identities` rc=0（本机 agent 里 0 个身份，属环境而非 API 问题）。
  补丁 0009 就是改 publickey blob 属性解析的（`Too many publickey attributes`），
  打完补丁这 13 个用例的 rc 与文案与 M0a-05 逐条一致，没有副作用。

## 7. spike #6 抽查 + 路径预言机复跑

**#6 readdir/stat 比值（ADR §6 第 5 条只要求抽查）**，零延迟本机 loopback：

| 测量 | 本轮（10 补丁产物） | M0a-04 零延迟 | 判定 |
|---|---|---|---|
| readdir 一次列完 1000 条 | 28.9 ms（0.03 ms/条） | 29.9 ms（0.03 ms/条） | 复现 |
| 逐条 stat 1000 条 | 366.9 ms（0.37 ms/条） | 368.4 ms（0.37 ms/条） | 复现 |
| 比值 | **12.7×** | 12.3× | 复现 |

M0a-04 里那个"52–54×"是 **1 s RTT** 那一档（readdir 被流水线化所以每条只花 0.019 个 RTT，
stat 每条正好 1 个 RTT，比值随 RTT 线性放大）。本轮在零延迟档抽查，不能拿 52× 来比——
"逐条 stat 是 readdir 的十倍到几十倍、必须靠目录列表一次拿全"这条结论不变。

**小文件并发排序**：这轮拿两个有效的补丁版样本对照（8 补丁 16:33 / 10 补丁 16:51，同一台机器）：

| 方案 | 8 补丁 个/s（CPU） | 10 补丁 个/s（CPU） |
|---|---|---|
| A 8 session 分片 | 2355.8（0.23 核） | 1055.7（0.17 核） |
| A 4 session 分片 | 1931.4（0.19 核） | 1130.2（0.19 核） |
| A 2 session 分片 | 1759.6（0.15 核） | 495.8（0.10 核） |
| 单 channel 攒 close | 1069.3（0.09 核） | 390.2（0.09 核） |
| 单 channel 串行 | 825.2（0.08 核） | 382.4（0.07 核） |
| 上传（单 channel） | 1204.7（0.08 核） | 595.1（0.08 核） |
| 每文件新建连接（50 个） | 32.3（0.04 核） | 11.9（0.02 核） |

- **站得住的是大档位差，不是相邻档位**：多 session ≥ 单 channel ≫ 每文件新建连接，
  最后一档与前两档差 **30–90 倍**，两轮都是这个数量级 ⇒ M0a-04 结论 4 复现。
- **2 / 4 / 8 session 之间排序不稳**：8 补丁那轮 8 > 4 > 2，10 补丁这轮 **4 > 8 > 2**。
  绝对个/s 在同一台机器上摆 2 倍以上（后台有构建任务时更甚），
  所以 **M0b 不把任何"个/s"或"几路最优"当硬预算**，池大小的上限留给 M1 用真实链路定。
  上一版文档写的"排序稳定：8 > 4 > 2"是拿两轮里恰好同向的样本说事，已撤回。
- CPU 随 session 数上升（0.07 → 0.17/0.23 核）方向一致，但同样只在 2 倍以内，不作预算。

**路径预言机（M0b-01 的 26 条用例）**在正式产物上三台服务器各跑一遍：

```
2201：一致 20，不一致 0，解析失败 0，双方都拒绝 1，仅服务器拒绝 5   最多往返 43
2202：同上                                                          最多往返 45
2203：同上                                                          最多往返 45
```

三台的**判定分布逐格相同**；往返数 43 vs 45 的差不是服务器分歧，是登录目录深度不同
（2201 是 atmoz chroot 后的 `/`，2202/2203 是 `/home/tester`，软链成环那条要多的组件正是这两级）。

这里把 M0b-01 记的"一致 21"改成了 **20**：21 是 `spike paths` 汇总行自己算错的——
它按 `rows.count − 硬失败 − 仅服务器拒绝` 得出"一致"，漏减了那 1 条"双方都拒绝"，
于是 20+1+5=26 的行被报成 21+1+5=27。逐行统计过三种判定各 20/5/1 才对得上，代码已修。
M0b-01 的**结论不受影响**（三台一字不差、`PathResolver` 不需要按服务器分叉），只是那个计数写错了。
除计数外，26 条用例的逐条判定与 M0b-01 一字不差 ⇒ `PathResolver` 不需要按服务器分叉，
相对路径 / `~` / 不存在路径这三条约束照旧。

唯一变化是 `symlink_ex` 的返回码（§0 结论 4）。M0b-01 当时预留了这句话：
"这是 libssh2 侧的问题，换 #14 锁定 commit 的静态库后必须重测"——重测结果：**问题仍在，且是补丁带来的**。
`spike paths` 现在按实测数据打判定，不再写死"返回码不可信"：

```
rc/status 分布：-31/71 … -31/131（16 条全部回读确认已建成）
负向对照（父目录不存在）：rc=-31 status=134 链不存在
（有回读已建成功但返回码非 0 的条目：后端只能按回读判定成功）
```

`status` 值 71、75、79…131 **每条 +4**，负向对照正好是序列的下一个 134——它不是服务器状态码
（合法上界 21），是被读到的某个递增量。三台服务器完全相同，说明是本机库的行为，不是服务端差异。

# 1. 建产物（首次约 5–8 分钟；OpenSSL 与 libssh2 分别有缓存，补丁集哈希变了才重编 libssh2）

docker exec ferry-sftp-modern-1 tc qdisc add dev eth0 root netem delay 1000ms
SPIKE_POLL_TIMEOUTS=50,200,1000 SPIKE_CANCEL_MODES=parked,setup "$BIN" cancel
SPIKE_CANCEL_ABORT=1  SPIKE_POLL_TIMEOUTS=200 SPIKE_CANCEL_MODES=parked,setup "$BIN" cancel
