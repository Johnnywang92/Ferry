# M1-05 · 目录列表接入 PathResolver / CharsetConverter / ErrorTaxonomy

M1'-5 的实测留档：`SFTPConnection.list` / `resolve` 这条正式路径上，一张目录清单要发多少个包、
readdir 的属性包里到底给得出哪几位、软链的解析结果缓存能省下多少往返、字符集是不是真的只作用在
显示层、以及失败被分成哪两类。数字全部来自钉版 libssh2（1.11.1_DEV + 10 条 CVE 补丁）+ 正式
Swift 实现，五台服务器各跑同一套语料。

## 0. 结论先说

| # | 结论 | 影响 |
|---|---|---|
| 1 | **一张清单只花 readdir**：1002 条目录 = 11 个 SSH_FXP_NAME 包 / 1005 次 `readdir_ex`，`stat` 增量为 **0**，五台一致。摊下来 **0.015–0.034 ms/条目**（本机回环）。 | ADR-0001 D8（禁止逐条 stat）在正式实现里成立，清单大小与往返数只跟包数有关 |
| 2 | **readdir 的属性包给得出五个字段，给不出属主名**：`size`/`permissions`/`mtime`/`uid`/`gid` 在 1002 条 × 五台上缺失数全为 0；`owner`/`group` 全为 nil。 | 类型判定只能用 `permissions & 0o170000`（M0b-01 的 `S_IS*` 宏不可导入）；显示属主名要么另发一次 `name/uid@openssh.com` 扩展查询，要么只出数字（§3.2） |
| 3 | **软链解析缓存挂在清单上，第二遍 0 次往返**：13 条链第一轮 286 次请求（273 段 lstat + 13 次 readlink），第二轮 **查询=0 命中=13**，`staleResolutionCount=0`。 | M0b-01 §0 结论 7 的"单次解析 4–11 次往返"只发生在**首遍**；同目录批量比对不按 RTT 计费 |
| 4 | **`lstat` 先行是唯一能判"这段是不是链"的办法**：0008 补丁（CVE-2025-15661）把 `sftp_symlink()` 的 `SSH_FXP_STATUS` 分支读坏了，那一族的 `libssh2_sftp_last_error` 返回的是**请求 id**，不是状态码（§9 原始 C 实测）。 | 走链的段探测一律 lstat→（确认是链才）readlink；`symlink_ex` 那一族的失败不采信状态，报 `undetermined` 并硬拆连接 |
| 5 | **`-38 BUFFER_TOO_SMALL` 一次涨档就够**：1504 字节的链目标从 1 KB 起、×4 涨到 4 KB，**涨档=1**、拿到 1504 字节原文；1002 条目录 **涨档=0**（NAME_MAX 255 < 1024）。 | 容量起点 1 KB 定得对；涨档必须**重来同一条**而不是跳过（sftp.c 状态机没推进） |
| 6 | **字符集只作用在显示层（R5）**：GBK 名按字节在 1002 条里命中，连接配 GBK 解出 `gbk-文件.txt`，同一份 `wireBytes` 按 UTF-8 解只能出 `\x2f\x62…` 转义——寻址字节一个都没动。 | `RemotePath.wireBytes` 权威不变；比较策略（大小写/归一化）取自连接配置，不取自路径字节 |
| 7 | **失败两类，phase 分得开**：服务器明说的 `NO_SUCH_FILE`/`PERMISSION_DENIED` 之后 `phase` 仍是 `authenticated`，同一条连接接着用；`symlink_ex` 那一族的失败判不出成因 → `aborted`。 | 同步引擎换路径重试不必重连；"判不出成因"不许伪装成"可重试的网络错" |
| 8 | **一条连接一条通道**：全过程 `channelInits=1`、`线程数=2`（≤2）。 | D7 单线程触碰纪律与 M0a-01 的多次 `sftp_init` 结论在正式路径上没有回潮 |

## 1. 列表这一层要回答的四件事

| 问题 | 结论 |
|---|---|
| 相对路径与 `~` 谁处理？ | 只有 `PathResolver`。服务器对 `./flat` 回 `NO_SUCH_FILE`、对 `~` 压根不展开（M0b-01 §0 结论 2/3），所以 `list` 在发出任何字节之前先 `lexicalResolve(path, relativeTo: home)`；`home` 由 `realpath(".")` 给（2201 是 `/`，其余四台 `/home/tester`，同一份容器内路径在不同服务器视图里长度差 11 字节）。 |

| 错误码怎么配成对？ | `rc` 与 `libssh2_sftp_last_error` 必须**同一次调用内即时取**；且 `symlink_ex` 那一族取到的不是状态码（§9）。 |
| 软链结果存哪？ | 存进这张 `RemoteDirectoryListing`：`probes`（段→目标，含"问过、不是链"的负结果）与 `resolutions`（条目→解析结果）。 |

## 2. D8：readdir 一次到底

| 端口 | 条目 | 观测 | `readdir_ex` 调用 | 包(估) | stat 增量 | 涨档 | ms |
|---|---|---|---|---|---|---|---|
| 2201 | 1002 | 1004 | 1005 | 11 | 0 | 0 | 21 |
| 2202 | 1002 | 1004 | 1005 | 11 | 0 | 0 | 16 |
| 2203 | 1002 | 1004 | 1005 | 11 | 0 | 0 | 15 |
| 2204 | 1002 | 1004 | 1005 | 11 | 0 | 0 | 15 |
| 2205 | 1002 | 1004 | 1005 | 11 | 0 | 0 | 34 |

`观测` 比 `条目` 多 2：libssh2 把 `.` 与 `..` 也交出来，`readDirectory` 丢弃它们（M0a-04 §4.2 的
"数量与清单一致"这条断言要连这两个一起算）。1005 = 1002 条 + 1 条终止的 `STATUS/EOF` + 2 个
被丢掉的点条目。**包数 11** 才是 RTT 的真数：一个 SSH_FXP_NAME 包平均装 ~93 条，五台都是 11 包。
对照 M0a-04 的逐条 stat = 52–54 × readdir——若 `list` 里给每条补一次 stat，这 11 个包会变成
1002 个包，跨洋按 1 s RTT 是 16.7 分钟对 11 秒。

`撞名=0`：`RemoteDirectoryListing.duplicatePaths` 在这套语料上没有命中。同一条路径重复三遍只列一次
（Core 单测钉住），因为静默覆盖是同步引擎最坏的失效方式。

## 3. 属性包的边界

### 3.1 五个字段都在，一个都没退化

1002 条 × 五台：`缺 size=0 缺权限位=0 缺 mtime=0 缺 uid/gid=0`，`sizeIsExact=false` 与
`mtimeIsReliable=false` 各 0 条。类型分布 `file:1002`（`flat` 全是普通文件），`links` 那张清单
13 条全部判成 `.symbolicLink`——判定依据是 `permissions & 0o170000 == 0o120000`，不是 `S_ISLNK`。

这一条在 M0b-03 之前只能算推测：`libssh2_sftp_readdir_ex` 传 `attr=nil` 会丢扩展段，传了结构体才
解析。现在正式实现走 `readdir_ex(handle, buf, size, nil, 0, &attrs)`（attrs 传结构体、attrs 长度传 0），
实测就是"五个字段都给得出"。

### 3.2 属主名给不出，且不是我们的选择

`owner/group 非空的=0`（1002 × 五台）。`sftp_bin2attr` 只解析 `ATR_*` 四个位，服务器就算在
readdir 包里塞了名字也会被丢；OpenSSH 的 `owner@openssh.com` / `group@openssh.com` 扩展属性段
libssh2 不读。所以：

- 数字 `uid`/`gid` 一定拿得到（上面那行），文本名一定拿不到；
- UI 要显示名字，只能对**当前可见页**补发 `stat` + name/uid 扩展查询，这是 M4 的显示层优化，
  不进 `list`（否则就是 D8 禁止的那件事）；
- 权限比较一律用数字 uid，不用名字——名字在不同服务器上可能不同。

`mtime` 是秒精度（`SSH_FXP_NAME` 里就是 uint32 秒），没有纳秒。同步引擎比对"远端是否更新"时，
**同秒内的改动看不出来**，这一条要写进 M4 的比对策略，不能在这里假装精度更高。

## 4. 软链：清单缓存与 RTT 记账

13 条链在同一张 `links` 清单里。首遍（2201，括号内是 2202–2205 不同的值）：

| 条目 | 段数 | target | resolved | ms |
|---|---|---|---|---|
| `l_to_file` | 6（8） | `../dir/file` | `<home>/spike/list/dir/file` | 3 |
| `l_chain` | 1 | `l_to_file` | 同上 | 0 |
| `l_to_dir` | 1 | `../dir` | `<home>/spike/list/dir` | 0 |
| `maze05` | 4 | `../maze/dir1/file` | `<home>/spike/list/maze/dir1/file` | 1 |
| `maze01/02/03/04/06/07/08` | 各 1 | 同上 | 同上 | 0–1 |
| `l_broken` | 2 | `../dir/nowhere` | `<home>/spike/list/dir/nowhere` | 0 |
| `l_long` | 252（248） | 1504 字节 `…/flat/e0000/e0000/…` | 同左（词法结果） | 83–163 |

- **首遍**：段 lstat 273（271）次 + readlink 13 次 = **286（284）次请求**；
- **二遍**：`查询=0 命中=13`，**零请求**；
- `l_chain` 只花 1 段：它指向 `l_to_file`，而 `l_to_file` 的段已经在缓存里；
- 8 条 `mazeNN` 共用 `../maze/dir1/file`，只有第一条多问了几段；
- `l_broken` 是断链：`target` 有、`resolved` 是词法结果、没有 `notFound`——断链的解析结果必须
  留在清单上，否则"远端已删"会被当成"没解析过"而反复重问；
- `staleResolutionCount=0`：重新列一次之后，缓存里没有上一次清单的孤儿条目。

`l_long` 这一条是刻意造的上界：目标是 1504 字节的 `e0000/e0000/…`，每一段都要问一次 lstat，
于是 252（248）次。它同时证明两件事：① 段缓存对**重复段**有效（同一个名字在链里出现 251 次，
只问一次），② 深路径的解析代价是按段计的，跨洋按 80 ms RTT 算这一条要 20 s——所以
`resolve` 只能显式调用、结果必须缓存，绝不能进 `list`。

M0b-01 §0 结论 7 说"单次解析 4–11 次往返"：本轮普通链落在 **2–9 次**（1 段 + 1 readlink 起），
量法与那轮一致（lstat 先行），差别只在**同一张清单上的第二条链几乎免费**。

## 5. R5：字符集是连接设置，不是路径属性

连接按 GBK 配置时（`SPIKE_CHARSET` 默认）：

```
GBK 名字按字节命中=true   最长**名**=255 字节   最长整条路径=272（2201）/284（其余四台）字节
按配置显示 = /spike/list/flat/gbk-文件.txt
按 UTF-8 显示 = \x2f\x73\x70\x69\x6b\x65\x2f\x6c\x69\x73\x74\x2f\x66\x6c\x61\x74\x2f\x67\x62\x6b\x2d\xce\xc4\xbc\xfe\x2e\x74\x78\x74
```

- 匹配用**字节**：`lastComponent(entry.path.wireBytes) == "gbk-" + CE C4 BC FE + ".txt"`，
  五台全命中。按整条路径比会漏（前缀长度随 `home` 变），按字符串比会直接错——`CE C4` 不是合法
  UTF-8。
- 同一份 `wireBytes`，GBK 配置解出"文件"，UTF-8 配置解出转义视图。寻址、比较、下载落地用的
  字节一模一样。**这就是 R5 要的形状**：解不出来只影响显示，不影响操作。
- `PathPolicy` 取自连接配置（Core 单测钉住 `.caseSensitive` / `.normalizeForCompare`），
  不取自路径字节；否则同一个目录在两种字符集设置下会给出不同的大小写策略。
- 最长名 255 字节（NAME_MAX）能整条拿回来，且 `涨档=0`：1 KB 的缓冲装得下任何**单个**名字。
  NAME_MAX 管的是最后一段，不是整条路径——量错对象会得到 272/284 这个"看起来超过 255"的数。

## 6. `-38` 与缓冲容量

| 场景 | 涨档 | 结果 |
|---|---|---|
| 1002 条目录（最长名 255） | 0 | 全部读出 |
| 1504 字节的链目标 | 1 | 拿到 1504 字节原文，绝对路径判定正确，前 24 字节 = `/home/tester/spike/list/` |
| 1 MB 上限仍装不下 | — | 判 `protocolViolation`，不猜 `notFound` |

`-38` 不是服务器回的码，是 libssh2 本地的缓冲判定（`sftp.c:3950`），代价是一次**已经发出去的往返**：
请求发了、答案在 libssh2 里被丢掉。所以容量策略是"从 1 KB 起、×4 涨、重来这一条"。
成功返回的 `rc` 就是目标的原始字节数，直接按 `rc` 搬字节，**不过 `String`**——GBK 目标是合法字节
但不是合法 UTF-8，转一遍就丢（R5）。

## 7. 失败两类

| 调用 | 分类 | phase |
|---|---|---|
| `list <不存在>` | `notFound` | `authenticated` |
| `stat <不存在>` | `notFound` | `authenticated` |
| `list noperm`（`chmod 000`） | `permissionDenied` | `authenticated` |
| `lstat 普通文件` | ok | `authenticated` |
| `list ./spike/list/dir` | ok（相对解析的正例） | — |
| `list ./flat` | `notFound`（语料在 `<home>/spike/list/flat`，相对基准是 home） | `authenticated` |
| `list ~` | ok | — |
| `list` 名字含 NUL | `lexical(nulByte)`，没发出任何字节 | `authenticated` |
| 之后 `list dir` | ok | `authenticated` |
| `readlink 普通文件` | `ssh/undetermined(rc=-31)@readlink` | **`aborted`** |

前五行为一类：服务器明说了原因，transport 完好，调用方换个路径再调一次就行，不必重连
（M1-04 §2.2 同一条连接复用那套判据的直接延伸）。最后一行为另一类：`symlink_ex` 那一族拿不到
成因，`keepsTransportAfter` 的既有规则是"连服务器说了什么都不知道就别把这条 session 留给下一个人"，
于是硬拆。**这不是保守**：见 §9，那个位置上躺着的值会被读成 `noSuchFile`/`permissionDenied`，
而误判成 `notFound` 会让同步引擎删掉本地文件。

`list 名字含 NUL` 判成词法错误且不碰 transport，是 PathResolver 那条"路径出错就是全盘错，但不能
因此废掉一条已认证好的连接"的纪律。

## 8. D7 / 通道复用

`合计：通道=1`、`线程数=2`（要求 ≤2）、全过程 11 次 `list` + 2 次 `stat` + 数百次链相关调用
共用这一条 `LIBSSH2_SFTP`。Core 侧的取消与超时纪律不变，本轮没有新增触碰 session 的线程。

## 9. `symlink_ex` 的状态码取自哪一格（原始 C）

起因：接 `ErrorTaxonomy` 之后，`readlink` 的失败分类给出一串合法值域（0…21）之外的数
（33–45、71–134），且**每发都不一样**。另开一条连接、绕开全部正式代码，直接问 libssh2：

| 调用 | rc | `last_error` | 本次请求 id | session errno | target 前 8 字节 | 判读 |
|---|---|---|---|---|---|---|
| READLINK 不存在 | **0** | 0 | **0** | 0 | `a5 a5 a5 a5 a5 a5 a5 a5` | **假成功**：rc=0 但出参一格没写 |
| READLINK 不存在 | -31 | 1 | 1 | -31 | 未写 | last_errno 就是请求 id |
| READLINK 不存在 | -31 | 2 | 2 | -31 | 未写 | 会被读成 `NO_SUCH_FILE`（猜对了，但纯属巧合） |
| READLINK 普通文件 | -31 | 3 | 3 | -31 | 未写 | 会被读成 `PERMISSION_DENIED`，服务器实际回 `INVALID_FILENAME(20)` |
| STAT 普通文件 ×24 | — | — | 4…27 | — | — | 只为把计数器推过 21 |
| READLINK 不存在 | -31 | **28** | **28** | -31 | 未写 | 28 落进 `LIBSSH2_FX_*` 值域之外，怎么配都配不出成因 |
| STAT 不存在（对照） | -31 | **2** | 29 | -31 | — | 真实状态码 |
| LSTAT 不存在（对照） | -31 | **2** | 30 | -31 | — | 真实状态码 |
| READLINK 真链（正例） | **11** | 0 | 31 | 0 | `../dir/f` | 成功路径可信 |
| REALPATH 穿过普通文件 | -31 | 32 | 32 | -31 | 未写 | last_errno 就是请求 id |

五台逐字相同。8 发被服务器拒绝，其中 5 发的 `last_error` 恰等于自己的请求 id，且全在 symlink
这一条路上；紧挨着的 STAT/LSTAT 仍给出真实的 `2 (NO_SUCH_FILE)`。

源码对照（`ThirdParty/build/src/libssh2/src/sftp.c`，补丁 0008 = 上游 `2dae3024897e`，
为修 CVE-2025-15661）：`sftp_symlink()` 的 STATUS 分支在 **3909–3922** 这几行——

```c
3909:    if(packet_type == SSH_FXP_STATUS) {
3911:        if(_libssh2_get_u32(&buf, &tmp_u32)) {          // ← 取的是**请求 id**
3916:        retcode = (int)tmp_u32;
3922:            sftp->last_errno = retcode;                 // ← 请求序号被当成状态码存下
3928:    /* advance past id */                                // ← 真正读 id 的那一步在 STATUS 之后
```

`SSH_FXP_STATUS` 的线格式是 `type(1) + request-id(4) + status-code(4) + message + lang`，
所以 3911 那一格读到的是 id，而 3916 把它当状态码；`else` 分支（NAME）才是需要 advance-past-id
的那个。打补丁前的写法是 `_libssh2_ntohu32(data + 5)`（偏移 5 = 跳过 type 与 id），
`sftp.c` 里其余各处的 STATUS 处理至今仍是这个正确写法，例如 2229 行
`retcode = _libssh2_ntohu32(data + 5);`（`sftp_write` 的 STATUS 分支）。
**只有 symlink 这一处被改坏**，上游 master 同样错，且比我们再多错一格（NAME 分支缺
advance-past-id，我们的补丁把它救回来了，就是 3928 那行）。

由此定下两条实现纪律（都已在代码与测试里钉住）：

1. **走链的段探测 lstat 先行**（`SFTPFileSystem.readlinkOrNil`）。"这段是不是链"由 lstat 的
   类型位回答——那是可信的状态通道；READLINK 只发给确认是链的那一段，正常必成。代价：非链段
   1 次往返、链段 2 次；换来的是断链、`..` 链、指向目录的链在五台上全部解析成功，且 §4 的首遍/二遍
   记账成立。`readlink` 与 `realpath(".")` 这两个 API 保持直发（`RemoteFileSystem` 的契约就是
   "必须能读非链的路径"），但它们的失败一律不采信状态码。
2. **`symlink_ex` 那一族的失败报 `undetermined`**（`sftpFailure(…, statusTrustworthy: false)`）。
   绝不把请求 id 当状态码分类——`2` 会伪装成 `notFound`（同步引擎误删本地文件）、`7` 会伪装成
   `connectionLost`（`isRetryable=true`，把确定性失败变成重试风暴）、`0` 会伪装成 `FX_OK`
   与"调用失败"自相矛盾。诊断 token 因此稳定为 `ssh/undetermined(rc=-31)@<operation>`，
   可以直接当聚合键用。

上游那一条（本地补一个补丁 0011，把 `sftp_symlink()` 的 STATUS 分支恢复成 `data + 5` 的语义，
再重出钉版 xcframework 并在 SecurityBaseline 记偏离）本轮**没有做**：它会改动签名过的第三方产物
与那份基线文档，属于要用户点头的方向选择。当前两条纪律不依赖它，补上之后 `readlink` 的失败
成因才谈得上可读——已记为待办，见 `ThirdParty/patches/README.md`。

## 10. 这一轮改了什么

| 位置 | 改动 | 为什么 |
|---|---|---|
| `SFTPFileSystem.readlinkOrNil` | 由"直发 READLINK 后按状态码判不是链"改为 **lstat 先行** | §9：不是链时 READLINK 会失败，而失败状态读不出来 |
