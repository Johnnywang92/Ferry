# M0b-02：字符集往返实测——为什么"解出来再编回去"不能当同一个名字

对应方案风险 R5（编码转换有损）。测量工具：`Spike/Sources/SpikeRunner/CharsetProbe.swift`，
运行 `cd Spike && swift build && .build/debug/SpikeRunner charset`。
被测的是 macOS 26 SDK 的 Foundation/CoreFoundation；换系统版本要重跑，别把这里的数字当协议保证。

## 结论先说

1. **CF 编号写错不会报错，只会全都解不出。** 本模块用到的 7 个 CF 编号换算出的
   NSString 编码全部有效：GBK 0x0631→2147485233、GB18030 0x0632→2147485234、
   Big5 0x0A03→2147486211、EUC-CN 0x0930→2147486000、Shift-JIS 0x0A01→2147486209、
   CP932 0x0420→8、EUC-KR 0x0940→2147486016。
2. **多字节字符集里只有 GBK 逐字节可往返**，其余都有失配。全 65536 个双字节组合的"解出来→编回去"结果：

   | 字符集 | 可解 | 往返失配 | 失配形态 | 例子 |
   |---|---|---|---|---|
   | GBK | 40244 | 0 | — | — |
   | GB18030 | 40581 | 258 | 编回成不同字节 | `80` → `€` → `A2 E3` |
   | Big5 | 29838 | 7 | 解得出编不回去 | `A3 75` → `ㄆ` → 拒绝 |
   | EUC-CN | 31274 | 7445 | 编回成不同字节 | `A1 21` → 全角空格 → `A1 A1` |
   | EUC-KR | 24796 | 94 | 解得出编不回去 | `FE A1` → 私用区字符 → 拒绝 |
   | Shift-JIS(0x0A01) | 45850 | 46 | 两种都有 | `81 7F` → `÷` → `81 80`；`88 40` → `∮` → 拒绝 |
   | CP932(0x0420) | 46345 | 658 | 两种都有 | `85 40` → `①` → `87 40` |
   | isoLatin1 | 65536 | 0 | 单字节码，无一对多 | — |
   | windowsCP1252 | 63001 | 0 | 同上，5 个空位解不出 | — |
   | UTF-8 | 18304 | 0 | 良序列恒等往返 | — |

   GBK 有效区（lead `81–FE`、trail `40–FE` 去掉 `7F`，共 23940 个组合）里 GBK 可解 23860、失配 0。
3. **Swift 的 `String.Encoding.shiftJIS`（rawValue 8）其实是 CP932**，等于 CF 0x0420；
   真正的 JIS X 0208 Shift-JIS 只有 CF 0x0A01 才是。区分用例：`87 40` 在 0x0A01 下解不出、
   在 0x0420 下解出 `①`；`81 7C` 分别解出 `−`(U+2212) 与 `－`(U+FF0D)。
   所以字符集必须显式走 CF 编号，不能图省事用 `String.Encoding` 成员名。
4. **自动探测不成立**：同一份 `D6 D0 CE C4`（GBK 的"中文"）——GBK/GB18030/EUC-CN 三个都解出"中文"，
   Big5 解出"笢恅"、EUC-KR 解出"櫓匡"、Shift-JIS 与 CP932 解出"ﾖﾐﾎﾄ"、latin1/cp1252 解出"ÖÐÎÄ"。
   九个候选全部"解得出来"，其中三个还解成有意义的词。命中多个不构成证据，
   字符集只能是连接上的配置项，配错了由解码出处标记（`Decoded.charset`）暴露给用户。
5. **整条编码会静默丢字符**：`"\u{FEFF}A"` 在 GBK 下整条 `data(using:)` 返回 `[41]`，
   "成功"且没有任何失败信号，名字短了一截。逐字符编码时 `FEFF` 单独返回**空 Data**（不是 nil），
   所以判定必须同时拒绝 nil 与空——这就是 `CharsetConverter.encode` 逐字符走的原因。

## 对实现的约束

| 约束 | 出处 |
|---|---|
| 显示与寻址分离：解码结果只进 UI，`wireBytes` 不变 | 结论 2 的失配列 |
| 禁止 decode→改→encode 当作同一条路径 | Big5/EUC-KR 的"编不回去"、EUC-CN 的字节替换 |
| 编码方向逐字符判定，空 Data 也算失败 | 结论 5 |
| 字符集为连接配置，UI 带出处标记 | 结论 4 |
| 规则不按字符集分叉，即使 GBK 零失配 | 结论 2；换成别的码表就没这保证 |

## 未覆盖

- Windows 版 SMB/FTP 服务器上的真实字节（本地只有 macOS 的码表；CP932/GBK 在 Windows 上由系统 ANSI 码页决定，
  这里的数字只代表 Foundation 的实现）。
- GB18030 的四字节序列（本次只扫了双字节组合，四字节区的失配面更大）。
- EUC-TW、JOHAB、windows-1250 系等未纳入 `Charset` 枚举的码表。
