## 0. 结论先说

| # | 结论 | 实测数字 | 影响与规范 |
|---|---|---|---|
| 1 | **大文件上下传极速对齐** | 本机回环 16 MB 下载跑出 **92–134 MB/s**；上传跑出 **56–101 MB/s**（老系统 2205 亦达 42 MB/s 下载、36 MB/s 上传）。 | 64KB/256KB/1MB 均稳定，默认 chunk 定为 256 KB 兼顾内存与吞吐 |
| 2 | **上传确认轮次严格等于 1.00** | 每 chunk 的 `writeCredits / writeChunks` 严格等于 **1.00**，五台一致。 | 非阻塞/重驱机制让每个 chunk 一次确认完，无无效轮询 |
| 3 | **短覆盖长必须带 `FXF_TRUNC`** | 用 4 MB 覆盖 16 MB，带 TRUNC 远端精确为 4,194,304 字节；裸 C 验证不带 TRUNC 远端残留 16 MB 旧尾巴。 | 彻底杜绝静默损坏，`createWrite` 默认带截断 |
| 4 | **取消打断毫秒级响应并硬拆连接** | `task.cancel()` 到抛出 `CancellationError` 净时 **0.0–13.8 ms**，连接立即转为 `.aborted`。 | 句柄级标志 + 连接级硬拆（D4/K1）；取消不破坏新请求，但会话不再复用 |
| 5 | **传输途中同通道交错列目录零增量** | 16 MB 下载期间同通道并发插播 `list()` 成功 8 轮共 **8016 条**，失败 0 次，**通道增量为 0**。 | 同一 session 上穿插元数据查询无需另开 channel，无死锁 |
| 6 | **边界文件（小/空/整块/跨包）完全吻合** | `empty.bin` (0B)、`small.txt` (12B)、`one256k.bin` (262144B)、`odd30001.bin` (30001B) 字节比对 100% 准确。 | FileHandle EOF 判定与跨 SFTP 包界限（30000B）逻辑严密 |
| 7 | **五台服务器均支持 `fsync@openssh.com`** | 裸 C 验证五台 `libssh2_sftp_fsync` 全部返回 `rc=0, session码=0, sftp码=0`。 | 安全落盘扩展面全覆盖 |
| 8 | **写队列未排空关闭将导致通道损坏** | 一发写后立即关闭在脏通道上报 `-37 (would block)` 或 `-7`，后续请求拒绝。 | 再次验证传输被中断时必须硬拆连接、不能复用原 session |

## 2. 参照校验、交错列目录与边界测试

### 2.1 参照哈希与交错并发

- **独立哈希 Sidecar 对账**：各服务器先下载 `.sha256` 签名再下 `rand4m.bin`，本地计算 CryptoKit SHA-256 与远端 coreutils 校验码全量 5 台 **100% 一致**。
- **传输途中插播 `list()`**：
  在 16 MB 下载同时，同通道发起 8 轮 `list("spike/list/flat")`：
  - 成功列出条目：**8,016 条**（8 遍 × 1,002 条）。
  - 失败次数：**0 次**。
  - 新增通道数：**0 条**（同一通道交替穿插，无挂死、无冲突）。

### 2.2 边界尺寸测试

| 文件用例 | 实际下载大小 | 语料预期大小 | 校验结果 | 说明 |
|---|---|---|---|---|
| `small.txt` | 12 字节 | 12 字节 | 一致 | 单包短文件 |
| `empty.bin` | 0 字节 | 0 字节 | 一致 | 0 字节 EOF 判定，一次未读路径 |
| `one256k.bin` | 262,144 字节 | 262,144 字节 | 一致 | 刚好对齐单 chunk 上限 |
| `odd30001.bin` | 30,001 字节 | 30,001 字节 | 一致 | 跨一个 SFTP 底层包边界（30,000 字节 + 1 字节） |

### 2.3 取消探针（`cancel()` 破坏性测试）

在 2205 上，在传输中途触发 `task.cancel()`：
- `settle`: 300 ms
- `cancel() → 抛出`: **13.8 ms**
- 抛出结果: `CancellationError`
- 连接 Phase: `.aborted`
- 之后同 session 再次发 list: 失败（`network/connectionLost`）
- 本地残留文件: 13,290,000 字节半成品（验证了断点保护与 M3 `.part` 文件机制的必要性）。

## 3. 裸 C 特征实测（`SpikeRunner xfer-raw`）

直接绕过 Swift 抽象层调用 libssh2 裸 C API，验证 4 个关键协议事实：

1. **`fsync` 扩展**：
   `libssh2_sftp_fsync` 在全部 5 台服务器上返回 `rc=0, session码=0, sftp码=0`，表明 OpenSSH 系列对 `fsync@openssh.com` 有完整支持。
2. **写队列未排空关闭（Dirty Drain）**：
   一发非阻塞 write 交出 16MB 数据，在未全部确认时直接调 `libssh2_sftp_close_handle`：
   - 2201–2204：close 均返回 `-37 (LIBSSH2_ERROR_EAGAIN)`，在驱动 20 片后仍无法完成；随后在该通道上发新请求被服务器拒绝。
   - 结论：**中途取消不能复用连接，必须硬拆 socket（D4 决策生效）**。
3. **`FXF_TRUNC` 覆盖验证**：
   用 100,000 字节写入原为 3,000,000 字节的文件：
   - 不带 `LIBSSH2_FXF_TRUNC`：文件大小保持为 **3,000,000 字节**（严重静默损坏）。
   - 带 `LIBSSH2_FXF_TRUNC`：文件大小精确为 **100,000 字节**。
4. **半途放弃 READ**：
   在读到 256KB 并在 `EAGAIN` 处停手后，保持通道并在阻塞模式下恢复：
   后续 STAT、新句柄读、readdir 数据流均能正确对齐，未发生字节错位。
