# Spike #2/#3 · 三种并发方案的吞吐、CPU 与请求重叠

日期：2026-10-15
环境：arm64 macOS，libssh2 1.11.1（Homebrew，链接 OpenSSL 4.0.3）
服务器：`sftp-modern`（alpine 3.20 / OpenSSH 9.7，`MaxSessions 10`），端口 2202
负载文件：`/home/tester/spike/big.bin` 64 MB；小请求 8 × 1 KB
测量：`Spike/Sources/SpikeRunner/ThroughputSpike.swift`，`spike throughput` / `spike latency`

---

## 0. 结论先说

| # | 结论 | 影响 |
|---|---|---|
| 1 | **libssh2 不支持同一个 SFTP channel 上有多个未完成请求**。第二个 handle 发 read 立刻返回 `LIBSSH2_ERROR_SFTP_PROTOCOL(-31)`，`sftp_last_error=0`，错误串 `sftp_read() internal error`。对照组（同 channel、同样多 handle、但一次只压一个请求）完全正常，速度等同单 handle ⇒ 失败来自**并发请求**，不是多 handle。<br>该结论与注入延迟无关（15 ms 与 0 ms 两轮都复现）。 | **方案 C（请求流水线）在 libssh2 上不可实现**，从架构候选里删除。要做"C 的效果"只能绕过 libssh2 自己发 fxp_read 包，本期不做 |
| 2 | **单 Session 多 Channel 不产生请求重叠收益，反而成倍变慢**（下表）。channel 数越多，每个请求的均摊耗时越高。 | **方案 B 的并发换不来 RTT 隐藏**。单连接多 channel 的价值只剩"少几次 TCP 握手与认证"，不能当吞吐手段 |
| 3 | **大文件吞吐只有靠增加 TCP 连接才涨**：15 ms 延迟下单连接 32.5 MB/s，8 连接 89 MB/s。 | 传输层的并发单位是 **Session**，不是 channel，也不是请求 |
| 4 | **客户端 CPU 成本与方案无关**：所有方案都在 190~240 MB/s/核。非阻塞 poll 机器本身不额外收费（非阻塞 1 channel ≈ 阻塞串行）。 | 选 A 还是 B 不该用"省 CPU"来论证；I1 里每 chunk 一次 memcpy 的代价也测不出来 |
| 5 | **每次传输新建 session/channel/handle 很贵**：本地 8 条连接跑 8 个 1 KB 请求要 188 ms（23.5 ms/请求），复用单 channel 串行只要 0.62 ms/请求。 | 小文件批量传输必须**复用连接与已开 channel**；连接的建立/认证放在队列外层，不放在每个文件上 |
| 6 | **libssh2 单次 `sftp_read(256 KB)` 真能返回 262144 B**，说明它按内部 32 KB 分包并已自动 read-ahead。 | 上层不需要再造一层"请求流水线"；I1 的 256 KB chunk 是合理的 |

## 1. 吞吐与 CPU（64 MB，256 KB 请求，15 ms 注入延迟，各 3 轮取中位数）

| 方案 | 并发 | MB/s | 占用核数 |
|---|---|---|---|
| 基准 | 1 | 125.0 | 0.52 |
| A 多Session池 | 8 | 124.6 | 0.58 |
| B 单Session多Channel | 8 | 136.7 | 0.65 |
| C' 同Channel串行(对照) | 8 | 155.1 | 0.69 |

本地回环经 Docker 用户态转发（vpnkit）吞吐被压在 ~130 MB/s，三个方案与基准的差异小于抖动（波动列 ±20%），**说明"本地吞吐"这一维度根本没有判别力**——这也是为什么要补 §3 的重叠实验，而不是拿 §2 的数字做架构决策。

## 3. 请求重叠实验（8 × 1 KB 小请求）

设计要点：`非阻塞 1Channel` 与 `非阻塞 kChannel` 走**同一份 poll 代码**，只差 channel 数，因此两侧差值就是"并发请求是否真的重叠"，排除了 harness 自身开销。

| 组合 | 注入 15 ms 延迟（ms/请求） | 无延迟（ms/请求） |
|---|---|---|
| 阻塞串行 1Channel | 20.73 | 0.66 |
| 非阻塞 1Channel | 19.49 | 0.62 |
| 非阻塞 2Channel | 30.01 | 0.59 |
| 非阻塞 4Channel | 59.46 | 1.60 |
| 非阻塞 8Channel | 106.53 | 2.33 |
| 非阻塞 1Channel × 8Handle（方案 C） | 失败 -31 | 失败 -31 |
| 多Session 2 连接 | 55.23 | 5.91 |
| 多Session 4 连接 | 88.35 | 11.60 |
| 多Session 8 连接 | 154.30 | 23.50 |

读法：
- 非阻塞 1Channel ≈ 阻塞串行 ⇒ poll 机器无额外成本，测量可信。
- channel 越多越慢，且在**没有延迟时也一样**（8 channel 比 1 channel 慢 3.7 倍）⇒ 不是 netem 或转发链路的问题，是 libssh2 在多 channel 间分发响应包的开销，且并发没有隐藏任何一次往返。
- 多Session 小请求最慢，但计时里含了每条连接的 `channel open + sftp_init + file open`（各需若干往返）。这正好量化出结论 5：**建连接的固定成本 ≈ 20 ms 量级**，小文件绝不能按文件建连接。

## 4. 对架构的落点（喂给 ADR-0001）

1. 候选方案从三个变成两个：**A 多 Session** 与 **B 单 Session 多 Channel**；C 出局（libssh2 不支持）。
2. 传输并发单位是 Session：大文件并行度 = 并行连接数，受服务端 `MaxSessions`/`MaxStartups` 与防火墙连接数约束。
3. 单连接内的多 channel **不用于提速**，只用于"同一连接上的不同用途不互相阻塞"（例如列目录与在传的字节流分离），并且实测并发小请求反而更慢，因此队列的并发度要落在连接维度而不是 channel 维度。
4. 小文件批量：单连接 + 单 channel + 串行 + 连接复用；这条路径的收益比任何并发手段都大（0.62 ms/请求 vs 23.5 ms/请求）。
5. `RemoteConnection` 的句柄形态（I1）不受影响；但 `RemoteFileSystem` 的并发语义要在 ADR 里写清：**同一连接上的多个 handle 不保证并发**。

## 5. 复测边界（必须写进 ADR 的保留意见）

- 本轮全部数据来自 **Docker Desktop 的用户态端口转发 + 容器内 netem 单向 15 ms**。绝对 MB/s、甚至"A 比 B 好多少"的比例都不可外推到真实 WAN；结论 1（同 channel 不能并发）与结论 3（poll 机器自身无额外成本）是 API 层事实，可在任何环境复用。
- **待办**：M1' 用一台真实 VPS（有公网 RTT 20~80 ms）重跑 §1/§3，确认 A 的扩展性与 B 的惩罚曲线；libssh2 需换成 M0b 锁定的 OpenSSL 3.x 构建重跑（Homebrew 这份链的是 OpenSSL 4.0.3）。
- 本轮只测下载。上传方向（含 `SSH_FX_EOF` 前的写入合并行为）未覆盖，M3 需补。
