# M1-06 · 单文件上下传：正式路径 + libssh2 内部四件事

M1'-6 的实测留档：`TransferEngine`（Core 泵）+ `SFTPConnection.openRead/createWrite/read/write/sync/release`
（Backends 句柄族）这条正式路径上，16 MB 单文件上下传要发多少个包、字节级正确性怎么验、
覆盖截断什么时候发生、传输途中能不能列目录、取消落在哪里 session 会怎样；以及四件只在 libssh2
内部发生、正式路径已经绕开的事（`fsync` 扩展支持面、不排空就关闭、`FXF_TRUNC`、半途放弃 READ）。
数字全部来自钉版 libssh2（1.11.1_DEV + 10 条 CVE 补丁）+ 正式 Swift 实现，五台服务器各跑同一套语料。

## 0. 结论先说

| # | 结论 | 影响 |
|---|---|---|
| 1 | **五台 × 3 个 chunk 档，16 MB 上下传全部字节级正确**：下载与服务器侧 `sha256sum` sidecar 对账、上传与远端 `stat` 大小对账，零不符；`rand4m.bin` 独立参照校验五台全中。 | M1'-6 出口标准"单文件上下传可用"成立，且不挑服务器年代 |
| 2 | **一次 `read` 可以搬走多个包，一次 `write` 只确认一个包**：16 MB 下载的 `read` 调用数（172–556）远小于 `ceil(16MB/30000)=560`；上传的 `write` 调用数精确等于 `chunk 数 × ceil(chunk/30000)`（768/576/560），且每次调用都拿到正数确认。 | 下载侧 libssh2 会合并同时到达的包；上传侧一个 chunk 要被拆成 ⌈chunk/30000⌉ 次往返，chunk 越大摊得越薄 |
| 3 | **`FXF_TRUNC` 是覆盖正确性的必要条件，不是优化**：不带它用 100000 字节盖 3000000 字节的旧文件，五台全部留下 3000000 字节的旧尾巴（静默损坏）；带上即 100000。 | `createWrite(offset: 0)` 必须带 `FXF_TRUNC`；`offset > 0` 才不截断 |
| 4 | **`fsync@openssh.com` 五台全支持（rc=0）**：`commit()` 里的 `libssh2_sftp_fsync` 不需要为"服务器不支持"准备失败路径，但保留该分支不亏（老服务器上它就是兜底）。 | M3 的 `.part` 收尾可以直接依赖 fsync 成功 |
| 5 | **不排空就关闭 = 通道报废**：非阻塞下发完整 16 MB 后立即 `close_handle`，五台的 STAT 全部问不到，其中四台连新句柄都开不出来；只有 2202 扛住，新句柄按每发 30000 字节继续确认。 | 正式路径的"写必须等 ACK 才返回"纪律（`RemoteWriter.write` 契约）被反向验证：在途未确认的块会被 close 静默丢弃 |
| 6 | **取消的 session 命运取决于取消落在哪里**：落在 chunk 之间（reader 预检）→ `CancellationError` 绕过闸门，session 存活（`authenticated`，后续 list 可用）；落在 chunk 之内（`drive` 循环顶部）→ 过闸门硬拆，session 转 `aborted`。同一 settle=300 ms 在 2205 上两次跑出两种结果。 | 与 `SFTPTransfer.swift` 注释声称的"一旦抛出即硬拆"不符，见 §5；这是 M1'-6 留下的唯一待决设计问题 |
| 7 | **一条连接一条通道贯穿全部传输**：五台合计 `channelInits=1`，传输途中 8 遍 `list`（8016 条）零失败、通道增量 0。 | M0a-02"chunk 之间挤得进别的请求"在正式实现上成立；控制面与传输面可以共用一条 session |
| 8 | **线程数=3，但执行仍串行**：传输负载（TaskGroup + Task 扇出）让 actor 在 3 条 GCD 线程上跑过；串行队列保证任意两个 C 调用不重叠，D7 实质成立，"固定单线程"的更强读法不成立。 | M1-05 的"线程数=2"是列表负载下的数，不是可以依赖的上界 |

## 1. 下载：远端 16 MB → 本地（正式路径）

`TransferEngine.download` + `openRead` + `read(maxBytes:)`，每档跑一遍，传完就地与服务器侧
`mid16m.bin.sha256` 对账（第一版曾拿本地随机源文件当参照物——两份随机内容本就不同，永远报
"不一致"，参照物必须是服务器侧 coreutils 算的那份）。

| 端口 | chunk=65536 | | chunk=262144 | | chunk=1048576 | |
|---|---|---|---|---|---|---|
| | ms / MB/s / read调用 | | ms / MB/s / read调用 | | ms / MB/s / read调用 | |
| 2201 | 164.3 / 97.4 / 394 | | 109.0 / 146.8 / 213 | | 265.6 / 60.3 / 220 | |
| 2202 | 124.0 / 129.0 / 389 | | 100.2 / 159.7 / 172 | | 102.6 / 155.9 / 131 | |
| 2203 | 153.2 / 104.4 / 404 | | 104.6 / 152.9 / 200 | | 104.6 / 153.0 / 131 | |
| 2204 | 108.3 / 147.8 / 399 | | 104.2 / 153.5 / 217 | | 97.4 / 164.2 / 142 | |
| 2205 | 400.3 / 40.0 / 553 | | 434.8 / 36.8 / 548 | | 394.5 / 40.6 / 556 | |

- **sha 不符 = 0**（五台 × 三档，静默通过；对账逻辑只在不符时打印）。
- 本地图层不是瓶颈：造 16 MB 46.5 ms、分块读 16 MB 2.5 ms（同步 `FileHandle`，256 KB 一块）。
- `read` 调用数远小于 560（= 16 MB / 30000 字节包上限）：本地回环下多个包同时到达，一次
  `libssh2_sftp_read` 可以搬走多个包（单发最多搬 90000 字节的实证见 §7 ④(c)）。包数才是 RTT
  的真数，调用数不是。
- 进度节流落在 100–200 ms 区间内（ADR-0001 §4.4）：16 MB 全程 2–5 次回调，最小间隔 8.6–162.6 ms
  （8.6 ms 那次是 2201 的首块抢跑，属噪声；其余均 ≥ 间隔要求）。
- 2205 与其余四台差 3–4 倍且与 chunk 档无关：Rosetta 转译 + 老 OpenSSH 的 CPU 瓶颈，
  与 M0a-01 对 atmoz 的观察同因。吞吐类结论不以 2205 为代表。

## 2. 上传：本地 16 MB → 远端（正式路径）

`createWrite(offset: 0)`（带 `FXF_TRUNC`）+ `write(_:)` + `commit()`（`fsync` + 释放句柄）。

| 端口 | chunk=65536 | | chunk=262144 | | chunk=1048576 | |
|---|---|---|---|---|---|---|
| | ms / MB/s / write调用=确认轮 | | 同左 | | 同左 | |
| 2201 | 383.6 / 41.7 / 768=768 | | 167.2 / 95.7 / 576=576 | | 131.1 / 122.1 / 560=560 | |
| 2202 | 235.0 / 68.1 / 768=768 | | 149.0 / 107.3 / 576=576 | | 143.1 / 111.8 / 560=560 | |
| 2203 | 232.1 / 68.9 / 768=768 | | 156.9 / 102.0 / 576=576 | | 144.9 / 110.4 / 560=560 | |
| 2204 | 219.1 / 73.0 / 768=768 | | 154.7 / 103.4 / 576=576 | | 141.0 / 113.4 / 560=560 | |
| 2205 | 580.9 / 27.5 / 768=768 | | 496.7 / 32.2 / 576=576 | | 402.4 / 39.8 / 560=560 | |

- **write 调用数 = chunk 数 × ⌈chunk/30000⌉**：65536→3 发、262144→9 发、1048576→35 发，
  五台逐字相同。一次 `writeChunk` 只换来一个包的确认（30000 字节），这是上传往返数的主项。
- **确认轮 / write 调用 = 1.00**：每次调用都拿到正数确认，`zeroMeansStall` 那条"回 0 当停顿重驱"
  的分支在正式路径上一次都没触发（裸 C 对照组同样 0 次，见 §7 ②）。分支保留：它是防御，
  不是已证伪的路径。
- 上传系统性慢于下载（2202 同档 112 vs 156 MB/s）：每个包一次 actor hop + 一次 drive，
  下载侧一次调用能合并多个包。M3 要再提速时的方向就在这里，不在 chunk 大小。
- 传完 `stat` 复核：远端大小 = 返回值，五台 × 三档零不符。
- **短文件覆盖长文件**：16 MB 传完用 4 MB 覆盖，五台全部 `16777216 → 4194304 字节 截断生效`。
  这就是 §7 ③ 那条"旧尾巴"在正式路径上的反面印证。
- 权限位固定 `0644`（`LIBSSH2_SFTP_S_IRUSR|IWUSR|IRGRP|IROTH`）：五台都收，本地权限搬运是 M3。

## 4. 传输途中交错列目录

下载 16 MB 的同时，同一任务组里每 30 ms 发一遍 `list(spike/list/flat)`（1002 条）：

| 端口 | 下载结果 | list 成功 | 条目合计 | 失败 | 通道增量 |
|---|---|---|---|---|---|
| 2201–2205 | 全部 16777216 字节 | 各 8 遍 | 各 8016 条 | 0 | **0** |

M0a-02 结论 1（同一通道不许两个请求同时在途，第二个回 -31）在这里的表现是：chunk 与 chunk
之间是真空的，`list` 从那些缝里挤进去，八遍全成、一条新通道都没开。控制面与传输面共用一条
session 的形状成立——但注意这是"串行缝隙里插队"，不是并发：传输吞吐会为此让出打包时间。

## 5. 取消：落点决定 session 的命运（本轮唯一待决问题）

`cancelProbe` 量两个数：`cancel()` 到抛错多久、之后这条 session 还能不能用。settle=300 ms 时
快服务器上 16 MB 早已传完（"没抛错（跑完了）"），所以补了一组 settle 扫描（2202）：

| settle | 结果 | cancel()→抛出 | phase | 之后发 list |
|---|---|---|---|---|
| 20 ms | cancelled | 1.7 ms | **authenticated** | 还能用（3 条） |
| 40 ms | cancelled | 1.4 ms | **authenticated** | 还能用（3 条） |
| 60 ms | cancelled | 10.2 ms | **aborted** | 失败 |
| 80 ms | cancelled | 1.9 ms | **aborted** | 失败 |
| 100 / 150 / 200 ms | 没抛错（跑完了） | 0.0 ms | authenticated | 还能用 |

2205 上 settle=300 ms 两次运行分别得到 `authenticated`（2.3 ms）与 `aborted`（3.1 ms）——
**同一参数两种结果**，排除法只剩一个解释：取消被观察到的位置不同。

- 落在 **chunk 之间**：`SFTPFileReader.read` 的入口预检（`if handleCancel.isSet`）先抛
  `CancellationError`。这条路不经过 `filesystemCall` 的闸门，没有 `hardTeardown`，session
  原样存活——代价是远端句柄当时还开着（本轮已补 `reader.close()` 摘表，见 §8）。
- 落在 **chunk 之内**：`SessionLoop.drive` 循环顶部观察到标志，从 `filesystemCall` 的 body 里
  抛出，闸门按 `keepsTransportAfter` 判 `CancellationError` 为"不留 transport"→ `hardTeardown`
  → `.aborted`。list 随后失败。

抛错延迟 0–10.2 ms：标志在 `poll` 切片内置位时，要等这一片睡满才回到循环顶部（10.2 ms 那次）；
其余情况一个 actor hop 内就抛出。K1 的"取消必须即时"成立。

这与 `SFTPTransfer.swift` 头部注释声称的语义（"一旦 `CancellationError` 抛出，闸门按 K1/D4
硬拆并转 `.aborted`"）**不符**：预检那条路绕过了闸门。ADR-0001 D2/D4/D6 的方向是"取消边界 =
一条 session，取消即废"，按那个方向应当删掉 reader/writer 的入口预检、让所有取消都从 `drive`
抛出；若产品想要"取消后会话可复用"，则应改注释与契约、并明确句柄泄漏的收尾责任。
**本轮只记录事实，不擅自定**——这属于要用户点头的方向选择（同 M1-05 §9 上游补丁那条的处置）。

取消后本地留下半份文件（1038 万–1677 万字节）：`.part` 临时文件 + 完成后改名是 M3 的事，
本轮不做，但**必须做**——现在这个形状会被同步引擎当成成品。

## 6. 边界：小 / 空 / 整块 / 跨包

## 7. 裸 C 对照组：四件只在 libssh2 内部发生的事

每个实验各自开一条 session（② 会把通道弄脏，共用会让③④变成"脏状态的连带"）。
`SPIKE_ABANDON=16777216`（默认值，即 16 MB）。

### 7.1 `fsync` 扩展支持面

| 端口 | `libssh2_sftp_fsync` rc | session 码 | sftp 码 |
|---|---|---|---|
| 2201–2205 | **0** | 0 | 0 |

`fsync@openssh.com` 不是 RFC 4716 的一部分，但五台全部实现且成功。`commit()` 因此不需要
为"服务器不支持"准备失败路径；代码里保留 `opUnsupported` 的豁免分支不亏——它是给更老的
服务器留的兜底，不是给这五台。

### 7.2 不排空就关闭（②）

| 步骤 | 2201 | 2202 | 2203 | 2204 | 2205 |
|---|---|---|---|---|---|
| (a) 排空后关闭：远端字节 / write 调用 / 回 0 次数 | 16777216 / 560 / **0** | 同左 | 同左 | 同左 | 同左 |
| (b) 一发交 16 MB 的首发 rc | **-37 (EAGAIN)** | -37 | -37 | **30000** | 30000 |
| (b) close 的 rc（驱动片数） | -37（20） | **-7（1）** | -37（20） | -37（20） | -37（20） |
| (b) 之后 STAT | 问不到 | 问不到 | 问不到 | 问不到 | 问不到 |
| (c) 脏通道上新句柄 | open 失败 | **开成**：200 发确认 6000000/16777216，回 0 共 0 次 | open 失败 | open 失败 | open 失败 |

- 干净路径（(a)）560 次调用、每次恰好一个包（30000 字节）、**回 0 零次**——与正式路径
  §2 的 768/576/560 完全同构，"write 回 0 = 这轮没确认"这条现象在两种路径上都没复现。
- (b) 一发交完整 16 MB 后立即 close：2204/2205 的首发就确认了一个包（30000），2201–2203 首发
  EAGAIN（socket 还没收下第一片）。无论哪种，剩下的包都留在 `handle->packet_list` 里被 close
  静默 free（sftp.c:2751）。**服务器上到底丢了多少，换一条新连接也问不到**——脏通道上的 STAT
  自己就发不出去，`sftp_last_error` 恰好是 0，"问不到"不许读成"丢了 16 MB"。
- (c) 只有 2202 的通道扛住了脏关闭：新句柄按每发 30000 字节继续确认，实验的 200 发上限用完时
  已确认 6 MB。其余四台连句柄都开不出来。
- 产品侧对应纪律：`RemoteWriter.write` 必须等这一段被服务器 ACK 才返回（契约原文），
  `libssh2_sftp_close_handle` 会把未确认的在途块直接丢弃——差一个字节，续传就从错的位置开始。

### 7.3 `FXF_TRUNC`（③）

| 端口 | 不带 TRUNC 覆盖 | 带 TRUNC 覆盖 |
|---|---|---|
| 2201–2205 | **3000000**（旧尾巴还在） | 100000 |

100000 字节盖 3000000 字节的旧文件：不带 TRUNC 五台全部留着旧尾巴——**静默损坏**，
比覆盖失败更坏（文件大小看着对，内容是上一版本的残片）。这正是 §2 覆盖实验"截断生效"
的原始依据，也是 `createWrite(offset: 0)` 契约里"实现必须截断"那句話的出处。

### 7.4 半途放弃一次 READ（④）

设计意图：非阻塞读 256 KB，故意在第 21 片 EAGAIN 时停手，制造一个 `read_state != idle` 的
在途 READ，再看后续请求。**五台都没 parked**：256 KB 都在 20 片（1 s）内读完（poll 2–20 片），
本地回环太快，造不出在途状态。后续测量因此是"读完之后的通道"而不是"被打断的通道"：

| 步骤 | 结果 |
|---|---|
| (a) 立即发 STAT | rc=0，五台一致 |
| (b) 续读同一句柄至 EOF | 1048576/1048576 字节，逐字节比对**无错字节** |
| (c) 新句柄从 0 再读 | rc=30000（2201/2202）/ 262144（2203）/ 60000（2204）/ 90000（2205），均无错字节 |
| (d) 同通道 readdir | 19 条，正常 |

两个副产品：(c) 的 rc 差异是 §1"一次 read 可搬多个包"的直接证据——2204/2205 单发搬走
60000/90000 字节（2–3 个包）；要真正 parked 需要在慢链路上跑（容器有 `NET_ADMIN`，
可临时 `tc netem`，本轮未做——正式路径的取消探针（§5）已经回答了产品问题）。

## 8. 这一轮改了什么

| 位置 | 改动 | 为什么 |
|---|---|---|
| `TransferRawSpike.resolveHome` | `libssh2_sftp_realpath` 是**函数式宏**，Swift 导入不了（"function like macros not supported"）→ 改用宏展开体 `libssh2_sftp_symlink_ex(…, LIBSSH2_SFTP_REALPATH)`；顺带处理 2201 的 chroot（realpath 回 `/` 时拼空前缀） | 编译错误修复：头文件 `libssh2_sftp.h:372` 的宏在 Swift 侧不可见 |
| `TransferSpike` ① | sha 参照物从"本地随机源文件"改为"服务器侧 `mid16m.bin.sha256` sidecar" | 原比较永远失败：本地源与远端 mid16m 是两份不同的随机内容，字节不同是设计使然 |
| `TransferEngine.download` | 三条路径补 `reader.close()`：成功（EOF 后）、失败（catch 里）、本地文件开不出来（`openForWriting` 抛错时） | 验证发现的真实缺陷：原先**任何路径都不关 reader**，服务器侧 READ 句柄挂到连接关闭才回收，下载 N 个文件漏 N 个；上传路径本就有 commit/abort，下载不能没有 |
| `TransferEngine.upload` | `createWrite` 抛错时补 `source.close()` | 对称缺陷：远端开不出来时本地 fd 泄漏 |

`reader.close()` 在取消路径上不发 `SSH_FXP_CLOSE`（`releaseFile` 检查句柄级标志，D4），
只摘连接表里的 id——`hardTeardown` 之后那些指针已不是合法内存，留着就是 use-after-free。
