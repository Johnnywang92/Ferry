# M1-04：M1'-4 认证四类、`none` 探测的预算与取消粒度

对应任务 #20。出口标准（v2.3 §加密后端与私钥 / §认证，ADR-0000 §9 N4）：密码、公钥（文件与内存两条入口，**不做 Swift 层预解密**）、keyboard-interactive、ssh-agent（临时 agent 环境）四类都在真服务器上走过；错误分类接 `ErrorTaxonomy`，`-16` 只在确认带口令时才敢说口令错；认证阶段的取消粒度有实测数字；带单测。

测量脚本：`Spike/Sources/SpikeRunner/AuthSpike.swift`（`SpikeRunner auth`，七节可用 `SPIKE_EXPERIMENT=tries|cancel|stuckagent` 单跑）。本文每一个数字都能在那份输出里找到。

## 0. 结论

1. **`libssh2_userauth_list` 每调一次就是一条 `USERAUTH_REQUEST(method=none)`，服务器照记一次认证尝试。** 实测：只调它不调任何认证，2202 与 2201 都在**第 7 次**拿到 NULL、`errno=-13 SOCKET_DISCONNECT`（两台都是 `MaxAuthTries 6`）。这条数直接决定了本轮改的一个真实缺陷，见结论 7。
2. **清单那块缓冲不归我们**：返回的就是 `session->userauth_list_data` 本身（userauth.c:230），`libssh2_session_free` 收尾时再放一次（session.c:1059）。调用方 `free` 它 = 让 session 揣着悬垂指针，到关闭时炸成 `pointer being freed was not allocated`（本轮真崩过）。而且**每次调用重新 ALLOC，地址每次都变**（实测三次三个地址），所以必须在同一趟里把字符串抄走——`[String]` 抄完，指针不再留。
3. **"认证失败之后清单会被服务器改写"这句话不成立**：五台在失败认证之后重新列出来的清单与首次**一字不差**（§1.3）。所以清单可以探一次就缓存。不配 Banner 时 `libssh2_userauth_banner` 五台全回 `-50 MISSING_USERAUTH_BANNER`，且这个值在 list 调用之后仍可取——本期不显示它（§8 待核 22）。
4. **私钥那 31 格里没有一格回 `-48`**：`frommemory`/`fromfile` 两条入口 × 五种语料 × 三种口令，凡是解析不出可用键一律 `-16 LIBSSH2_ERROR_FILE`。原因是 `_libssh2_pub_priv_keyfilememory`（openssl.c:4987）只看内层返回是否为 0，非 0 就换成 `-16` + `Unsupported private key file format`，pem.c:466 那条 `-48` 在这一步被丢掉；本来能把"口令错"单认出来的分支靠 `HAVE_SSLERROR_BAD_DECRYPT`，我们这份产物没定义它。**修正**：M1-03 之前写进代码注释的"老式 PEM 没给口令回 `-48`"是读源码推出来的，实测不成立（§3.2）。
5. **所以 `-16` 分三格只能靠两件事实**：这次带没带口令、头部探针说这把是不是加密的。三条 token 各落一格，实测都在真机上验过（§3.3）。附带一格：**明文私钥带了口令照样认证成功**（libssh2 直接把口令忽略），所以 UI 里"密钥本来就没错，用户多填了口令"不该报错。
6. **服务器"列了"不等于"会问"**：2201 的清单里有 `keyboard-interactive`，但它对请求直接回 `USERAUTH_FAILURE`，一条 `INFO_REQUEST` 都不发；空应答换来的 `-18` 只能报成 `badPassword`。反过来 2202/2203/2204 上选 kbdint 直接 `auth/methodNotOffered`，**依据是服务器自己列的清单，不是错误码**，应答者 0 次被调（§5）。
7. **本轮改掉的缺陷：我们自己把用户的口令额度烧掉了一半。** 认证失败不拆会话（结论 8）+ 每次重试都重探一次 `none` ⇒ 每次重试烧两格而不是 1 格。实测同一条 2202 连接上连错口令：改之前第 4 次就被服务器踢掉（`network/connectionLost`，phase 转 `aborted`），改之后 5 次都是 `auth/badPassword`、第 6 次才踢（§2.3）。修法是把首次探测的清单缓存在连接上（结论 3 证明敢缓存）。
8. **认证失败不拆 transport**：`.auth` 与 `.localIO` 让会话停在 `.ready`，换个凭据再调一次就行——免掉的正是 TCP 建连 + 密钥交换 + 那次 `none` 探测。取消、超时、socket 断是链路的事，硬拆转 `.aborted`（ADR-0001 D7 的例外表）。**但 bcrypt 那一轮 0.4–0.6 s 每调一次 `frommemory` 都要重付**，会话保留省不了它（实测：口令错 192–204 ms，口令对 398–426 ms）。
9. **keyboard-interactive 那条异步缝隙保住的是"置标志到退出等待"，不是"置标志到 C 调用返回"**：回调把 session 线程睡住，每 50 ms 回顶部查取消，实测答题期间置标志 → **77 ms** 返回（≈1.5 个切片）。代价是回调没有"返回错误"这条路，取消那一趟的**空应答还是发出去了**，服务器上白记一次失败认证（§4.3）。等用户答题的时长从网络预算里扣掉，所以"找验证码 40 秒"不会被判成超时。
10. **agent 路的失败码分成两半**：没有 `SSH_AUTH_SOCK` → `agent_connect` 回 `-39 BAD_USE` → `auth/agentUnavailable`（要修的是本机环境变量，不是服务器上的 `authorized_keys`）；socket 指向不存在的文件 → `-42 AGENT_PROTOCOL` + `failed connecting with agent`。分步计时：`connect` 0 ms、`list_identities` 0 ms、`userauth` 17–18 ms。
11. **挂起不回话的 agent 会把认证卡死，这是本期已知的取消粒度上限**：对面对 Unix socket 只 listen 不回话时，`agent_connect` 照样回 0（TCP 三次握手进队列就成功），`agent_list_identities` **5000 ms 没返回**——那条 socket 是阻塞的，libssh2 明写没实现非阻塞（agent.c:110）。本期不修（要修得自己实现 agent 协议），出口标准里明写这条上限。
12. **纯 CPU 那一段打断不了**：bcrypt 期间置标志 → **135 ms** 抛出（对照组：不取消时认证本身 415 ms）。这与 M0a-03 那条"阻塞在 C 调用里只能等它自己回来"是同一条上限，不是回归。
13. **一条连接上不许换用户名**：同一条 session 上第二个用户名会让 sshd 直接断（`Change of username or service not allowed`，RFC 4252 §5.1）。这条是本轮踩出来的——第一次测"不存在的用户名"时复用同一条会话，拿到 `errno=-13`，一度误判成服务器异常（§1.4）。落到产品上是：**UI 里改了用户名必须重连**，不能就地换。
14. **测试**：Backends 34 条（本轮 +17），`FERRY_LIVE_SERVERS=1` + 临时 agent 下全绿；Core 87 条（本轮 +6）全绿。
15. 握手加认证之后 `Measure.executorThreads.count` 是 **1 或 2**，不是恒等于 1：串行执行器在两个 actor job 之间可能换 worker（D7 说的是"同一时刻只有一条线程在碰 session"，不是"进程生命周期内固定一条"）。所以认证这组的断言写成 `<= 2`，`keyboardInteractiveRoundTrip` 就是靠这条盯住"回调没有引出第三条线程"。

| 文件 / 类型 | 职责 |
|---|---|
| `Core/Connection/AuthenticationMethod.swift` | 四种方式的输入。`privateKey(PrivateKeyMaterial)` 只带字节与可选口令，**不带任何解密结果** |
| `Core/Connection/AuthenticatedSession.swift` | `AuthenticatedMethod`（含 `.none` 与 `.agent` 两格）+ `serverOfferedMethods` + `agentIdentity` |
| `Core/Connection/KeyboardInteractive.swift` | `KeyboardInteractivePrompt`（带线路上的 `echo`）/ `Request` / `Responder` |
| `Core/Connection/PrivateKeyEncryption.swift` | 只读头部的探针：`.plain` / `.encrypted` / `.unrecognized`。`-16` 能分成三格全靠它 |
| `Core/CrossCutting/ErrorTaxonomy.swift` | `AuthMethod` 七个入参 + `classifyAuth`；`-39`→`agentUnavailable`、`-16`/`-48` 的三格分流 |
| `Core/Model/RemoteError.swift` | `AuthFailure` 七格（`methodNotOffered`、`agentUnavailable` 由后端合成）；`isFatalToSession` |
| `Backends/SFTPAuthentication.swift` | 实现体：`none` 探测 → 方式闸门 → 四条驱动路径 → 单一出口 `finish` |
| `Backends/SFTPConnection.swift` | `offeredMethods` 缓存、`authAttempts` / `authElapsedMs` 计数、失败两类走向 |
| `Backends/SessionLoop.swift` | `drive(deadlineMs:pausedMs:)`：认证沿用握手那台机器，多一个"不计预算的等待时长" |

三处有意的形状决定：

- **成功与失败只有一个出口**（`finish`）。顺序要紧：先看回调里留下的"用户没答/取消"标志，再分类 `rc`。反过来的话那条空应答换来的 `-18` 会被报成"口令错"——那是谎报。
- **方式闸门在发凭据之前**：`requireMethod` 用服务器列过的清单判，所以 `methodNotOffered` 那一格 `authAttempts=0`，线路上一个凭据字节都没发（实测 2202 kbdint 44 ms、应答者 0 次被调）。
- **`SessionContext` 挂在 `session->abstract` 上**：kbdint 回调的参数里没有 session 指针（userauth.c:452），连接级的东西（应答者、等待时长、取消标志、线程号）只能放这唯一一个通道。

## 1. 认证前那次 `none` 探测

### 1.1 五台的清单

| 端口 | `libssh2_userauth_list` 原文 | 与 `sshd` 配置一致 |
|---|---|---|
| 2201 atmoz(8.4p1) | `publickey,password,keyboard-interactive` | 是（但 kbdint 问了也不答，§5.2） |
| 2202 modern(9.7) | `publickey,password` | 是 |
| 2203 legacy(9.7) | `publickey,password` | 是 |
| 2204 oldalgo(9.7) | `publickey,password` | 是 |
| 2205 oldos(6.7p1) | `publickey,password,keyboard-interactive` | 是，且真会问 |

非默认端口一律带 `tester` 用户名去列；`errno=0` 时返回的串按线路顺序切成 `[String]`，不做排序——诊断报告里它要和抓包对得上。

### 1.2 缓冲归属与地址

2202 三次连续调用的地址：`0x…800000` → `0x…800080` → `0x…800100`。同一条 session、同一个用户名、内容完全一样，**地址还是每次不同**。这两件事合起来定了实现：只读 + 同一趟抄成 Swift 值。

### 1.3 失败之后清单会不会被改写

五台各测一格：先列 → 故意发一个错口令（`rc=-18`）→ 再列。五台的"与首次相同"全部为 `true`，`errno` 全部 0。这条是 §2.3 那处缓存的依据；反过来说，如果哪天遇到一台会按认证进度改清单的服务器，缓存就会把用户挡在正确的方式外面——所以清单只缓存到**这条连接**上（`SFTPConnection` 状态），不落盘、不跨连接复用。

顺带两格：
- `banner rc=-50`（五台都没配 Banner），值在 list 之后仍可取。
- **不存在的用户名照样列出同一份清单**（新连接上测 `nosuchuser`）。所以"这台列出了 password"不等于"这个账号能用 password 登"，UI 不许把清单当成账号存在的证据。

### 1.4 每次调用烧一格 `MaxAuthTries`

只调 `userauth_list`、不做任何认证，直到拿不到清单：

| 端口 | 第几次拿到 NULL | `errno` | 该台的 `MaxAuthTries` |
|---|---|---|---|
| 2201 | 7 | `-13 SOCKET_DISCONNECT` | 6（默认） |
| 2202 | 7 | `-13` | 6（显式写进配置） |

配合 sshd 日志的形状（M1-01 那套容器）：`authenticate()` 一次 = `attempt N method none` 紧跟 `attempt N+1 method password`。**探测与凭据发的是同一个包序列**，`MaxAuthTries` 不区分方法。⇒ 每条连接的首次探测要在预算里给自己留一格，重试绝对不能再探一次。

## 2. 认证失败的两类走向

### 2.1 哪些错误保留 transport

| 抛出的错 | 会话 | 依据 |
|---|---|---|
| `.auth(*)` | 留，phase 停在 `.ready` | libssh2 收到 `USERAUTH_FAILURE` 后认证状态机干净回到 idle；实测换口令再调就过（`kbdintRetryWithNewAnswerReusesSession`） |
| `.localIO` | 留 | 私钥材料为空这种是**调用方的输入问题**，压根没碰网络（实测 `localIO/readFailed` 之后 phase 仍是 `.ready`） |
| `CancellationError` | 硬拆 → `.aborted` | D4：取消路径不做体面关闭 |
| `.network(.timeout)` / socket 断 | 硬拆 → `.aborted` | 状态不可信 |
| `.protocolViolation` | 硬拆 | 应答条数不符、`userauth` 回 0 但 session 说没认证等 |

口令错被判成 `aborted` 的实际后果是"UI 对用户说网络不行"，所以 `wrongPasswordKeepsSession` 里 phase 断言和 token 断言同等重要。

### 2.2 就地重试实测

2202，同一条连接，错口令 → 对口令：第一次 `auth/badPassword` 10 ms，第二次 `ok` 8 ms（`measure.authAttempts=2`，`authElapsedMs` 累计 19 ms）。免掉的正是 TCP + kex + 那次 `none` 探测。

但**不能**把它写成"自动重试"：`RemoteError.isRetryable` 里 `.auth` 一律不可重试，因为每发一次就烧服务器一格额度。免掉的也不是 bcrypt——加密私钥每一次 `frommemory` 都重付那 0.4 s（§0.8）。

### 2.3 预算：缓存清单前后对比

2202，同一条连接，固定错口令连打，直到服务器踢人：

| 轮次 | 缓存之前 | 缓存之后 |
|---|---|---|
| #1–#3 | `auth/badPassword` 9–10 ms | `auth/badPassword` 8–9 ms |
| #4 | **`network/connectionLost` 0 ms，phase=`aborted`** | `auth/badPassword` 8 ms |
| #5 | — | `auth/badPassword` 8 ms |
| #6 | — | `network/connectionLost` 8 ms，phase=`aborted` |

`MaxAuthTries 6` 是一台连接的总额度，`none` 探测自己也占一格。缓存之后用户在一台服务器上能犯的口令错误从 3 次变成 5 次——这是本轮唯一一处"测量把 UX 缺陷拽出来"的地方，测试 `retriesDoNotDoubleBurnServerAttempts` 钉住它。

另有一格口径要记：`Measure.authAttempts` 数的是"我们把凭据发出去几次"，**不含**首次 `none` 探测。所以诊断报告里它天然比 sshd 日志里的 `attempt N` 少 1；#23 契约测试如果要对外暴露"服务器第几轮"，得单开一个口径（§8 待核 26）。

## 3. 私钥：31 格矩阵与头部探针

### 3.1 矩阵（2202，`SPIKE_PORTS=2202 SpikeRunner auth` 第②节）

| 语料 | 头部判定 | 口令 | `frommemory` rc / ms | `fromfile` rc / ms | token |
|---|---|---|---|---|---|
| `ed_plain` | plain | 无 / 对 / **错** | 0 / 16–27 | 0 / 16–18 | 成功（口令被忽略） |
| `ed_bcrypt` | encrypted | 无 | **-16** / 0 | **-16** / 0 | `auth/passphraseRequired` |
| | | 对 | 0 / 426 | 0 / 401 | 成功 |
| | | 错 | **-16** / 194 | **-16** / 204 | `auth/passphraseIncorrect` |
| `rsa_new` | encrypted | 无 / 对 / 错 | -16/0 · 0/404 · -16/192 | -16/0 · 0/413 · -16/198 | 同上三格 |
| `ecdsa_new` | encrypted | 无 / 对 / 错 | -16/0 · 0/400 · -16/192 | -16/0 · 0/398 · -16/192 | 同上三格 |
| `rsa_pem`（老式 RFC 1421） | encrypted | 无 / 对 / 错 | -16/0 · 0/16 · -16/0 | -16/0 · 0/18 · -16/0 | 同上三格 |
| `garbage`（`PuTTY-User-Key-File-2` 头 + 一句瞎话） | unrecognized | 无 | **-16** / 0 | — | `auth/keyRejected` |

三点要看：

- **两条入口的码完全一致**，只有文案不同：`frommemory` 说 `Unsupported private key file format`，`fromfile` 说 `Wrong passphrase or invalid/unrecognized private key file format`。所以"文件入口能区分口令错"是错觉，不能用文案做分类。
- **老式 PEM 与新格式共用同一枚 `-16`**，没有第二枚码可用（这是本轮对 M1-03 期间那条注释的修正）。三格的分流因此 100% 依赖头部探针。
- **bcrypt 的耗时形状**：口令对 = 400 ms 量级（真要解密），口令错 = 195 ms 量级（一次解密尝试失败），无口令 = 0 ms（连解都没开始）。这三档差别本身就是可诊断的信号，`Measure.authElapsedMs` 留着它。

### 3.2 为什么没有 `-48`

`_libssh2_pub_priv_keyfilememory`（openssl.c:4987）的顺序是：先让 OpenSSL `PEM_read_bio_PrivateKey` 读——`openssh-key-v1` 它不认，加密 PEM 拿空口令也解不开——然后转去试 openssh 格式。那条路径里 pem.c:466 确实会返回 `-48 KEYFILE_AUTH_FAILED`，**但调用方只看 `st == 0`，非 0 一律换成 `-16 FILE`**。`fromfile` 的孪生函数（~4676）同样。本来能把"口令错"单认出来的那段在 `openssl.c:5037-5047`，靠 `HAVE_SSLERROR_BAD_DECRYPT`，我们这份 OpenSSL 3 产物里它没定义。

⇒ `ErrorTaxonomy` 的 `-48` 三行留着，但口径变了：它是**换 crypto 后端（mbedtls / 无后端）时的兜底**，不是本期可达的码。留着不会把 `-16` 说错，删掉会在换后端那天把 `passphraseRequired` 降级成 `keyRejected`。

### 3.3 三格分流只看两件事实

```
带口令？  ×  头部探针 = encrypted？
(true , _    ) → .encryptedKey                 → -16 ⇒ passphraseIncorrect
(false, enc  ) → .encryptedKeyWithoutPassphrase → -16 ⇒ passphraseRequired
(false, plain|unrecognized) → .plainKey        → -16 ⇒ keyRejected
```

实测各落一格（`privateKeyPassphraseSplitsThreeWays`、`legacyPemSharesTheSameCodeAsNewFormat`）。第三条是关键：**头部读不出加密形态就不许猜"缺口令"**。`garbage` 那格如果只看"没带口令"就报 `passphraseRequired`，用户会被支去"给一个根本没有口令的假密钥填口令"。

`encryptedKeyWithoutPassphrase` 之后 UI 的动作是"把口令填上再试"，同一连接就地重试即可（§2.2），不必重连。

## 4. keyboard-interactive：异步缝隙的三段

### 4.1 回调把 session 线程睡住

libssh2 的 kbdint 状态机没有"挂起—恢复"的口子：`LIBSSH2_USERAUTH_KBDINT_RESPONSE_FUNC` 在 `libssh2_userauth_keyboard_interactive_ex` **里面**被同步调用，返回时答案必须已经填好。而应答者是异步的 UI。缝法是：回调里起一条 `Task.detached` 去问应答者，session 线程在 `DispatchSemaphore` 上按 50 ms 切片等，每片回顶部查取消。

`detached` 是必需的，不是风格：`Task {}` 继承当前执行器，而当前正站在 session 那条串行执行器上，回调把这条线程睡了，继承过去的 Task 永远排不上——自己等自己。

应答者实现方有一条硬约束（写进协议文档注释）：**不许绕回同一条 session 执行器**。

### 4.2 等用户答题不烧网络预算

`SessionLoop.drive(deadlineMs:pausedMs:)` 的 `pausedMs` 把回调里累计的等待时长从预算里扣掉。没有它，"用户去找验证码 40 秒"会在 `authenticationTimeout`（30 s）上被判成 `network/timeout`，而那是网络故障的形状。

### 4.3 取消时空应答还是发出去了

回调没有"返回错误"这条路。取消或用户关框时我们**不填应答**，而 libssh2 会把 `CALLOC` 出来的空槽原样发出去（`_libssh2_store_str` 对长度 0 跳过 memcpy，misc.c:289）——于是服务器上照样记一次失败认证，白烧一格 `MaxAuthTries`。

能守住的是分类：`finish` 先看 `cancelledDuringPrompt` / `declinedPrompt` 标志，抛 `CancellationError`，绝不把换回来的 `-18` 报成 `badPassword`。实测：400 ms 后置标志 → 77 ms 返回 `cancelled`，phase=`aborted`（`cancelDuringPromptIsFastAndHonest`，断言 `latency <= 150`）。

### 4.4 关框与条数不符

- 应答者返回 `nil`（用户关掉对话框）⇒ `CancellationError`。与主机密钥那层的 `decline` 同形（ADR-0000 §11 H6 的同一个理由：用户主动中止不该报成"口令错"）。
- 应答条数与服务器问的条数不符 ⇒ `protocolViolation`，消息里带两边各是几条——这是这条违规唯一的线索。注意这一格**照样发了一次空应答**（同 §4.3），所以"别多答也别少答"是应答者实现方的责任，不是我们能替它兜住的。

实测两格都在 2205 上跑（`declinedAndMismatchedPrompts`），两格之后 phase 都是 `.aborted`（违规与取消都不留会话）。

这条对产品的影响是 UI 的：如果照着清单画"请输入服务器提示的答案"然后转圈，用户会等到 `authenticationTimeout`。所以清单只用来**排除**方式（`methodNotOffered`），不用来**承诺**方式。

### 5.3 失败比成功慢得多（2205）

2205 错口令 2356 ms / 2345 ms 两轮复现，同一次成功是 368 / 346 ms。那台是唯一 `UsePAM yes` 的（`docker/oldos/sshd_config:14`），PAM 的失败延迟正好是这个量级。`authenticationTimeout` 30 s 装得下，但**对话框必须显示进行中状态**：用户连错三次要看到 7 秒左右的等待，而它长得像卡住了。2202 同格 53 ms（另一次 632 ms 是抖动，第二轮起没复现，不记为结论）。

## 6. ssh-agent

### 6.1 分步计时与失败码

| 步骤 | 结果 |
|---|---|
| `libssh2_agent_init(session)` | 挂在已存在的 session 上才有返回；传 NULL 直接段错误（M0a-05 结论 4） |
| `agent_get_identity_path` | `<无>`（这份 libssh2 不填路径，只能靠环境变量） |
| `agent_connect` | rc=0，**0 ms** |
| `agent_list_identities` | rc=0，**0 ms** |
| `agent_userauth`（第 1 把，RSA） | rc=0，**17–18 ms** |

临时 agent 里实际有两条身份（RSA 2048 + ed25519），客户端先试 RSA，第一把就过了所以 ed25519 没轮到——与 M1-01 §5 的 `ssh -vv` 观察一致。**每把一次 `agent_userauth` 都是一次完整的 publickey 认证尝试**，这就是 §6.3 那个上限的理由。

失败码两格，落在不同的用户动作上：

| 条件 | 原始码 | token | 用户要修的东西 |
|---|---|---|---|
| 没有 `SSH_AUTH_SOCK` | `-39 BAD_USE`（agent.c:182 取不到 socket 名） | `auth/agentUnavailable` | 本机环境 / agent 没在跑 |
| socket 指向不存在的文件 | `-42 AGENT_PROTOCOL`，`failed connecting with agent` | `auth/keyRejected`（走会话层） | 环境变量里那个路径 |

第一格有专门测试（`agentWithoutSocketFailsCleanly`，只在 `SSH_AUTH_SOCK` 缺席时启用）：报成 `keyRejected` 会把用户支去查一个根本没收过这把钥匙的服务器。

### 6.2 挂起不回话的 agent：取消粒度上限

造一个只 `listen`、从不 `accept`、也不回数据的 AF_UNIX socket，把 `SSH_AUTH_SOCK` 指过去：

| 观测 | 结果 |
|---|---|
| `agent_connect` | **rc=0，0 ms**（连接进监听队列就算成功，不需要对面读） |
| `agent_list_identities` | **5000 ms 没返回**，判定为无限阻塞 |

那条 Unix socket 是阻塞的，libssh2 没给它非阻塞（agent.c:110 原文 "not yet implemented"）。⇒ agent 路上"置标志到停下"的粒度不是 50 ms，而是**等这一步自己回来**。本期不修：修它等于自己实现 agent 协议。产品上的后果与对策（#25）：选 agent 时先在本机探一次 socket 可读，或者给"用 ssh-agent 登录"这条按钮配一个明确的等待态与"改用密钥文件"的出口。

### 6.3 上限

`SFTPConnection.agentAttemptLimit = 5`：一把被拒（`-19` 查询阶段就不要 / `-18` 签名后被拒）就换下一把，第 6 把不试，抛 `auth/tooManyAuthAttempts`。留的那一格是给分类本身的。这枚 token 由后端合成，`classifyAuth` 不产出它（服务器多半直接断线 → `.network`）。本期没有"agent 里塞 6 把以上"的实测（脚本只装 2 把），所以这一格是策略而非实测，见 §8 待核 24。

## 7. 取消粒度（认证阶段）

| 场景 | 置标志之后 | 抛出 | phase | 对照组 |
|---|---|---|---|---|
| bcrypt 解私钥期间 | 立刻 | **135 ms** | `aborted` | 不取消时认证本身 415 ms（握手+认证全程 457 ms） |
| 等用户答题期间 | 立刻 | **77 ms**（≈1.5 个 50 ms 切片） | `aborted` | `authenticate` 总用时 404 ms |
| agent `list_identities` 阻塞 | — | 不返回（§6.2） | 不变 | 5 s 实验上限内没等到 |

第一行是 D3 的已知粒度上限而不是缺陷：`CancellationError` 只能在 C 调用返回后被 `drive` 循环顶部观察到，而 bcrypt 那 0.4–0.6 s 是纯 CPU、里面没有 poll 边界（与 M0a-03 那条阻塞打断同一条）。两行的结果都必须是 `cancelled`，不能是 `auth/passphraseIncorrect` 或 `auth/badPassword`。
