## 2. 无开发者账号的连带后果(需要你知情)

`v2.3` 里有两处出口标准现在无法成立,已按实际情况改写:

- **M0b 出口标准**原为"逐个签名 + Hardened Runtime + 公证跑通" → 改为"**逐层 ad-hoc 签名 + Hardened Runtime 下本地产物可启动**"。公证(Notarization)移出本期范围。
- **M6 交付**原含"公证打包 + Sparkle 自动更新" → Sparkle 仍可用(它依赖 Sparkle 自己的 EdDSA 签名密钥,不依赖 Apple 账号),但**更新包同样未经公证**。
- **实际分发限制**:未公证的 app 在别人的 Mac 上会被 Gatekeeper 拦截,用户需手动放行(右键打开,或 `xattr -d com.apple.quarantine`)。这与 D2=B"通用客户端发布"存在张力——面向陌生用户的发布体验会受损,而 Mac App Store 上架(D2=C)本期完全不可行。
- **测试环境风险**:M1' 要测 Keychain 与 `ssh-agent`,ad-hoc 签名与正式 Developer ID 产物在 Keychain 访问组、code requirement 稳定性上行为不同。**决定**:M1' 起在本地用固定自签证书(非 ad-hoc)做 Keychain 相关测试,避免每次重建后 Keychain 条目失效;若后续购买账号,需在 M6 前追加一轮"真实签名环境复测"。
  > 2026-10-15 M0b-04 实测修正:担心的一半没发生,另一半更糟。登录钥匙串条目在 cdhash / entitlements / 签名 Identifier 三种变化后**都还能读回**;"重建即失效"不成立。真正的问题是 **data-protection 钥匙串在 ad-hoc 下完全不可用**(`err -34018`),而补 `keychain-access-groups` entitlement 会让进程在 exec 阶段被 **SIGKILL**。"用固定自签证书"这条至今未执行——往用户钥匙串塞自签代码签名身份要改系统状态,需单独确认。详见 `docs/spike/M0b-04-签名与Hardened-Runtime走查.md` §6。

- 权威文档:`Mac SFTP FTP 客户端开发方案 v2.3(完整版).md`。

## 7. M0a spike 出口(2026-10-15 第三轮)

spike #1~#8 全部有结论,并发架构与取消机制已定案 → **`docs/ADR-0001-并发架构与取消机制.md`**。
实测记录:`docs/spike/M0a-01`…`M0a-05`。

本轮改写了 v2.3 的两条口径,后续验收按新口径:

| # | 项 | 原口径 | 新口径 |
|---|---|---|---|
| K1 | 取消验收 | "`Task.cancel()` 后 200ms 内真正停止网络传输" | **poll 切片 ≤ 50 ms,且取消路径禁止 libssh2 体面关闭**。理由:取消响应实测等于 poll 切片(50/200/1000 ms → 47.4/198.5/999.7 ms),200 ms 属压线;而"取消要 8 秒"的假象来自退出循环后的体面关闭(1 s RTT 下 7.9 s),掐 socket 只要 0.1 ms |
| K2 | 备用取消 | "量化同 session 其他 channel 一起失败的代价" | 代价已量化:**同 session 全量失败(3 条空闲 channel → 0),但失败检测 0.6 ms、`session_free` 毫秒级**。由此升级为硬约束:**一个取消边界独占一条 session** |

另有两条需要在 M0b/M1 补测(不影响定案):本机 loopback 吞吐受 Docker 转发 ~130 MB/s 上限,绝对数字需真机 WAN 复测;`posix-rename@openssh.com` 在不支持该扩展的真实设备上行为未测。
