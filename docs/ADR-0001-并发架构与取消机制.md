# ADR-0001 · 并发架构与取消机制定案

- 状态：**已接受**（2026-10-15，M0a spike #1–#8 全部有实测结论）
- 生效条件：§6 的"OpenSSL 3.x 重跑清单"完成前，本 ADR 的**相对结论**生效，**绝对数字**只作参考
- 相关文档：`docs/ADR-0000-启动前决策.md`、`docs/spike/M0a-01`…`M0a-05`、方案 v2.3 §并发模型与连接管理

---

## 1. 决策

| # | 决策 | 依据 |
|---|---|---|
| D1 | **并发单位是 session**（方案 A：控制面 1 条 + 传输面 N 条独立 session）。默认 N=3，硬上限 8。 | M0a-02：15 ms 延迟下单连接 32.5 MB/s，8 连接 89 MB/s；单 session 多 channel 在 2/4/8 档全部**不比单 channel 快**（35.2 / 36.3 / 39.5 MB/s） |
| D2 | **一个取消边界 = 一条 session**。不允许两个用户可取消的任务共用一条 session。 | M0a-03 §4：`shutdown(socket)` 会让同 session 其他 channel 3→0 全废，无法选择性掐一条 |
| D3 | **非阻塞 + `poll`，切片 50 ms**（v2.3 原文的 200 ms 只是"上限"，实测 200 ms 切片得 198.5 ms 属压线）。取消标志在"循环顶部"与"poll 超时"两处检查。 | M0a-03 §1：取消→循环退出 47.4 / 198.5 / 999.7 ms 与切片 50 / 200 / 1000 ms 一一对应 |
| D4 | **取消收尾用 `shutdown(fd, SHUT_RDWR)` → `session_free` → `close`；禁止在取消路径调用 `close_handle` / `sftp_shutdown` / `disconnect`。** | M0a-03 §2：1 s RTT 下体面关闭 7.9 s vs 掐 socket 0.1 ms；取消总代价 8.05 s → 0.20 s |
| D5 | **建阶段（握手、认证、`sftp_init`、`open`）也走同一个非阻塞状态机并检查取消标志。** | M0a-03 结论 4：阻塞建阶段里置标志后 3.5 s 才回到循环顶部，"连接中/打开中"根本点不动 |
| D6 | **session 三态：`ready` / `busy` / `aborted`**；`aborted` 只丢弃不回收。 | 同 D4；且被打断的会话返回码随卡在哪个调用而变（-36 / -43 / `Unable to startup channel`），不可复用 |
| D7 | **每条 session 一个专属串行 executor**，C 调用只在该 executor 上执行（v2.3 原方案保留）。 | libssh2 session 非线程安全；M0a-02 结论 4 证明非阻塞 poll 机器不额外收 CPU（190~240 MB/s/核，各方案一致） |
| D8 | **目录清单一律 `opendir + readdir` 一次拿全，比对在本地做；禁止逐条 stat。** | M0a-04：readdir 每条 0.019 RTT，逐条 stat 每条 1.0 RTT，差 52~54 倍；1 s RTT 下 1000 条 = 19.3 s vs 16.8 分钟 |
| D9 | **重命名拆两个接口**：`renameNative`（目标存在即失败）与 `replaceAtomically`（显式 `libssh2_sftp_posix_rename_ex`）。 | M0a-05 §2：`rename_ex` 给了 `OVERWRITE` 仍返回 `-31 / SSH_FX_FAILURE`；`posix_rename_ex` 两种情况都 rc=0 原子覆盖 |
| D10 | **私钥走 `libssh2_userauth_publickey_frommemory`，一个 session 生命周期只解析一次。** | M0a-05 §3：openssh-key-v1 + bcrypt 三种算法解析并认证成功；但解锁 0.45–0.5 s，比明文贵 20 倍 |

## 2. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **C 单 channel 请求流水线** | libssh2 **做不到**：同一 channel 上第二个未完成请求立刻 `LIBSSH2_ERROR_SFTP_PROTOCOL(-31)`，`sftp_read() internal error`；同 channel 串行的对照组正常 ⇒ 触发条件是并发请求而非多 handle。有延迟与无延迟两轮都复现（M0a-02 结论 1）。要做得绕过 libssh2 自拼 `SSH_FXP_READ`，本期不做 |
| **B 单 session 多 channel 作为并发手段** | 换不来 RTT 隐藏，反而**成倍抬高每请求成本**（M0a-02 结论 2）。B 剩下的唯一价值是"少几次 TCP 握手与认证"，而 M0a-04 显示复用 session+channel 已经拿到这个收益，不必再开多 channel |
| **体面关闭作为取消的一部分** | 1 s RTT 下 7.9 s（≈8 个往返），且这段被算进"取消延迟"就会产生"取消要 8 秒"的错误结论（M0a-03 §1/§2） |
| **`libssh2_session_set_abort_fn()`** | 1.11.1 **头文件无声明、dylib 无符号**（M0a-05 §1，链接期探针）。v2.3 "不把它作为前提"的保留意见现已转为定论 |
| **靠 socket 缓冲区调优救多 channel** | `SO_RCVBUF` 放大与"非阻塞 1 channel"对照都追平阻塞串行，说明瓶颈是协议往返不是窗口（M0a-02 §3） |

## 3. 连接池参数（M0b 起点）

| 参数 | 值 | 理由 |
|---|---|---|
| 控制面 session | 1 条/站点 | v2.3 原案。清单、stat、心跳不占传输连接 |
| 传输面默认并发 | **3** | v2.3 的"1 控制 + 3 传输"与实测一致：15 ms 下 3 条已在 68 MB/s 量级，再往上边际递减且撞服务端限制 |
| 传输面硬上限 | **8** | 容器显式 `MaxSessions 10`、`MaxStartups 10:30:100`；spike #1 实测两台都在**第 11 次** `sftp_init()` 失败（`-21 CHANNEL_FAILURE / Unable to startup channel`）。留 2 条余量给控制面与突发 |
| 小文件队列并发 | 3→8 **自适应**，按 `每文件RTT预算 × 文件数` 决定 | M0a-04 结论 5：小文件场景多 session 近线性（8 session 6.6×），与大文件只 2.7× 不同；1 s RTT 串行 1000 个 = 68 分钟，8 并发 = 13.5 分钟 |
| poll 切片 | 50 ms | D3 |
| 心跳 | `libssh2_keepalive_config/send`（可用） | M0a-05 §1 |
| 重连 | 指数退避 1s/2s/4s→30s 带抖动；传输中不自动重连（v2.3 原案） | 避免静默重试写坏文件（R2） |

## 4. Core 接口层面的连带约束

1. `RemoteFileService` 的 SFTP 实现里，**cancel 只能靠标志 + poll**，因此所有对外暴露的挂起操作（含 `connect`/`open`/`list`）必须跑在同一个非阻塞状态机上（D5）。这条决定了 M0b 的 `Session` 抽象不能只包"传输循环"。
2. 池的取还接口要能表达 `aborted`：任务结束返回时区分"可复用"与"作废丢弃"，作废的**不发 disconnect**，直接 `session_free` + `close`。
3. socket 不需要调用方设 `O_NONBLOCK`（libssh2 在 `set_blocking(0)` 后自行处理，M0a-03 结论 6 已对照验证）。
4. 进度回调要**节流合并（100–200 ms）**：实测"相邻文件完成的最大间隔"在 15 ms 档就有 435–1248 ms，每文件刷新一次必然抖。
5. 凭据错误分类自己实现：`-16 LIBSSH2_ERROR_FILE` 同时覆盖"文件读不到"与"口令错"，且 `frommemory` 的文案会把口令错说成"Unsupported private key file format"（M0a-05 §3）。
6. `libssh2_agent_init()` **必须传入已存在的 session**；传 `NULL` 直接段错误（不是返回错误码）。

## 5. 风险与未覆盖项

| 项 | 状态 |
|---|---|
| 绝对吞吐 | **不可信**。本机 loopback 走 Docker 用户态转发，有 ~130 MB/s 天花板；D1 的选型靠的是相对差值。真机 WAN 复测排在 M0b |
| 只测了下载 | 上传（`SSH_FXP_WRITE`）只在小文件档测了往返次数（3.0 RTT），大文件上传的窗口/背压行为未测 → M0b |
| 不支持 posix-rename 的服务器 | 未覆盖。三台仿真机都是 OpenSSH 系（都带扩展）。真实设备需 M1 补测，实现上先探测再退化到 `renameNative` + 冲突策略 |
| "UI 刷新是不是瓶颈" | 本轮只给出网络底数与回调间隔上界；真实 SwiftUI 进度绑定成本留 M1' 复测（M0a-04 §4） |
| 弱算法设备（S6） | 未测，属 M1' 范围 |

## 6. M0b 出口必测清单（OpenSSL 3.x xcframework）

本机 Homebrew libssh2 1.11.1 链接的是 **OpenSSL 4.0.3**，与最终 xcframework 不同源，
以下事实必须在锁定 commit + OpenSSL 3.x 后重跑，任何一条翻转都要回改本 ADR：

1. spike #4/#5 全部（取消三段计时、abort 收尾、连带失败）——crypto 后端换了会改变"清理"段以外的绝对值。
2. spike #7 链接期探针（`api-probe.sh` 改指 xcframework 的 include/lib 路径）。
3. spike #8 私钥格式（换后端后 `openssh-key-v1` + bcrypt 是否仍解析成功，`libssh2_crypto_engine()` 返回值）。
4. spike #2/#3 吞吐与 CPU（加密路径换实现，每核 MB/s 会变）。
5. spike #6 的 readdir/stat 比值（协议行为，预计不变，抽查即可）。
